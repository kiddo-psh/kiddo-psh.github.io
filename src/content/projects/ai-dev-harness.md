AI가 코드를 빨리 만들어도 팀원마다 다른 요구사항을 전달하면 통합할 때 다시 맞춰야 합니다. 같은 규칙을 배포한 뒤에도 그 규칙이 지켜졌는지, 어떤 작업에 사용량이 집중됐는지, 테스트가 실제 변경 코드를 검증했는지는 별도의 문제로 남습니다.

ai-dev-harness는 팀 공통 개발 절차를 새 저장소에 적용하는 키트에서 출발했습니다. 지금은 Claude Code와 Codex의 사용량, 작업에 연결된 검증 기록을 함께 다루는 도구로 확장하고 있습니다. 이 글에서는 팀 개발 경험에서 어떤 문제를 골랐고, 어디까지 구현·적용했는지 구분해 설명합니다.

## 같은 AI 도구를 쓰는데도 서로 다른 합의를 구현하고 있었다

주차바로를 개발할 때 팀원 대부분이 AI 코딩 도구를 사용했습니다. 도구는 비슷했지만 요구와 판단을 전달하는 방식은 달랐습니다. 사람끼리 합의하기 전에 구현을 시작하거나 서로 다르게 이해한 내용을 코드로 만드는 경우가 있었습니다.

다음 프로젝트인 feelm에서는 요구사항과 계약의 우선순위, 구현 전에 합의할 항목, 변경 위험에 따른 계획·리뷰·검증 절차를 공통 규칙으로 정리했습니다. 팀원들이 사용하는 모습을 보며 다른 팀에서도 재사용할 수 있게 만들고 싶었습니다.

다만 규칙을 도입한 경험과 완성된 키트의 효과는 다릅니다. feelm에서의 사용 경험은 키트화의 출발점이며, 이후 자동화 전체의 성과를 입증하는 자료는 아닙니다.

## 규칙 문서를 복사하는 대신 적용과 확인을 한 흐름으로 묶었다

저장소마다 기술 스택과 검증 명령이 다르고, 로컬에서 통과한 작업이 CI에서 실패하기도 했습니다. 문서를 복사한 뒤 수작업으로 고치면 어떤 차이가 의도된 설정이고 어떤 차이가 누락인지 알기 어려웠습니다.

원본 템플릿과 저장소 설정을 두고 `init`으로 파일을 생성하고 `check`로 원본에서 달라진 부분을 검사하도록 만들었습니다. 플랫폼·업무 추적 도구·영역별 검증 명령은 설정으로 분리하고, 키트 자신에게도 같은 방식을 적용했습니다.

| 팀에서 겪은 문제 | 키트에서 만든 대응 |
| --- | --- |
| 저장소마다 달라지는 규칙과 양식 | 설정에 따른 생성과 템플릿 이탈 검사 |
| 합의 전에 시작되는 구현 | 변경 위험에 따른 계획·리뷰 절차 |
| 로컬과 CI의 다른 검사 | 영역별 검증과 GitLab CI 설정 조각 |
| 사용량이 어디에 집중되는지 모름 | 세션·토큰·추정 비용 수집 |

파일이 같다는 사실만으로 개발 절차를 지켰다고 볼 수는 없습니다. 그래서 작업 중의 검사와 병합 시의 검사를 함께 뒀습니다.

## 작업할 때의 제한을 코드 병합 시점에도 확인했다

`judge`는 변경 경로를 보고 위험 단계를 제안합니다. Claude Code hooks는 도구 실행 시점에 개입하는 기능으로, 보호 경로의 편집을 차단하거나 확인을 요구하는 데 사용했습니다. GitLab CI는 MR 본문과 영역별 검증·보안 검사를 확인합니다.

경로만으로 모든 위험을 알아낼 수는 없습니다. 문장으로 설명해야 하는 위험은 사람이 판단하고, 도구는 실행 가능한 조건을 검사하도록 역할을 나눴습니다. 도구별 hooks 지원도 달라서 로컬 제한 하나에만 의존하지 않았습니다.

## 토큰이 부족해진 뒤에는 사용량의 출처를 알아야 했다

Claude Code 팀 플랜을 쓰며 토큰 부족을 반복해서 겪었습니다. 실행 방식을 바꾸려면 어느 사람·도구·모델·작업에 사용량이 집중되는지부터 확인해야 했습니다.

이 필요에서 AI 개발 도구의 실행을 수집하고 살펴보는 AgentOps 기능을 추가했습니다. 처음에는 세션·토큰·추정 비용·hooks 개입을 기록했고, 이후 Claude Code와 Codex를 같은 기준으로 비교하는 문제까지 다뤘습니다.

| 보고 싶은 내용 | 확인할 질문 |
| --- | --- |
| 팀 사용량 | 사람·도구·모델별로 토큰과 추정 비용이 어디에 쓰였나? |
| 수집 상태 | 기록이 들어오는가? 오류와 차단이 있었나? |
| 작업별 검증 | 어떤 작업에 어떤 테스트·리뷰·완료 조건이 연결됐나? |

로컬 대시보드와 함께 OTel Collector → Prometheus·Loki → Grafana로 이어지는 선택적 팀 관측 구성을 제공합니다. 아래는 저장소에서 공개한 **가상 팀원·목데이터 화면**이며 실제 팀의 비용이나 생산성 수치가 아닙니다.

## 같은 사용량이 두 번 더해지지 않도록 기준을 정했다

Codex의 내장 관측 기능과 키트가 읽는 세션 기록은 같은 사용량을 서로 다른 경로에서 볼 수 있습니다. 둘을 합하면 중복이 생깁니다. 세션의 누적 토큰을 매번 더해도 합계가 부풀려집니다.

공통 수집 v2에서는 사용량마다 안정적인 ID를 두고, 같은 기록은 다시 더하지 않도록 했습니다. 두 도구의 기록 형식을 공통 사건으로 맞추고 가격표와 발생 시각을 기준으로 집계합니다. 내장 관측 정보는 실시간 사용 여부를 보는 별도 원천으로 유지합니다.

| 합계를 왜곡할 수 있는 상황 | 처리 방식 |
| --- | --- |
| 재시도나 다른 작업 디렉터리에서 같은 기록을 재전송 | 같은 ID는 중복 합산하지 않음 |
| 기록이 늦게 도착 | 전송일 대신 사건 발생 시각의 KST 날짜에 귀속 |
| 전송 사이 가격표 변경 | 첫 전송 준비 시 단가를 저장해 재전송에도 유지 |
| 단가를 모르는 모델 | 토큰은 포함하고 비용은 부분 합계로 표시 |
| 전송 실패나 부분 거절 | 보내기 전에 로컬 전송 대기 목록에 저장하고 성공한 묶음만 완료 처리 |
| 검증 기록이 없거나 도구가 미지원 | 성공이나 0으로 채우지 않고 상태를 구분 |

과거 누적 형식의 로그와 7일을 넘겨 보내지 않은 기록은 복원에 한계가 있습니다. 합계를 제공할 때는 어떤 기록이 빠질 수 있는지까지 설명할 수 있어야 했습니다.

## ‘테스트 통과’가 어떤 코드와 작업의 결과인지 연결했다

사용량만으로 작업이 검증됐는지 알 수는 없습니다. 작업별 실행 근거를 수집하는 확장에서는 세션을 작업·PR·역할에 연결하고 검증, 사람의 개입, 질문 대기, 리뷰 상태를 별도로 기록합니다.

세션이 작업을 옮겼다면 뒤늦게 수집한 기록도 발생 당시 작업에 연결해야 합니다. 연결 이력을 시간 구간으로 보존하고, 자동 연결은 사용자가 활성화한 이후 같은 작업 디렉터리에서 시작한 새 세션에만 적용했습니다. 연결하기 전의 기록을 현재 작업에 자동 소급하지 않습니다.

테스트 실행에는 실행 ID와 전후 코드 상태를 식별하는 해시를 남깁니다. 실행 중 코드가 바뀌면 통과로 기록하지 않습니다. 완료 조건의 검증 수는 같은 작업에서 관측된 통과 실행과 코드 상태가 연결된 경우에만 증가시킵니다.

정형 질문과 답변은 대기 구간으로 연결하지만 일반 문구에서 승인·거절을 추정하지 않습니다. 리뷰 제안의 채택도 수정 완료나 검증 통과와 구분합니다. 직접 관측한 사실, 사람 신고, 에이전트 신고의 출처를 표시하며 기본 수집에서는 프롬프트·응답·코드 원문을 중앙으로 보내지 않습니다.

## 30초마다 확인하는 대신 작업이 끝나는 시점에 수집했다

꾸기에 적용하면서 30초 주기 수집을 제거하고, 완료 이벤트·PR 요약·수동 실행 때 한 번 수집한 뒤 종료하도록 바꿨습니다. 변화가 없으면 전송하지 않고 실패한 기록은 다음 이벤트에서 재시도합니다. Windows에서는 백그라운드 작업이 콘솔 창을 띄우지 않게 처리했습니다.

두 확장의 수집 계기는 다릅니다. 공통 v2는 Claude Code의 SessionEnd와 Codex Stop hook을 사용하고, 실행 근거 확장은 선택 설치한 Codex 완료 notify와 Claude 관측 Stop, PR 요약에서 수집합니다. 모든 환경을 하나의 상시 수집기가 처리하는 구조는 아닙니다.

Codex 비대화형 실행에서 프로젝트 hook이 동작하지 않는 등 한계도 있습니다. 자동 수집이 모든 실행을 덮는다고 가정하지 않고 수동 수집과 상태 진단을 제공합니다.

이후 꾸기 저장소에는 실행 근거 수집과 관측 구성을 적용했습니다.

## 출시한 기능과 개발 중인 확장을 구분했다
