## 1. 문제: 규칙을 적어 두는 것만으로는 부족했다

feelm에서는 AI 에이전트가 따를 규칙, 플랜과 분리 리뷰 절차, 검증 기준을 운영했습니다. 하지만 새 저장소마다 이를 복사하고 스택에 맞춰 수정해야 했고, 문서가 있어도 실제로 절차를 지켰는지 확인하려면 사람이 다시 살펴봐야 했습니다.

목표는 규칙을 더 길게 쓰는 것이 아니라 **시작할 때 설치할 수 있고, 작업 중 이탈을 발견하며, 적용 결과를 측정할 수 있게 하는 것**이었습니다. 기존 절차를 템플릿으로 옮기되 프로젝트마다 달라지는 플랫폼, 업무 추적 도구, 영역별 검증 명령은 설정으로 받게 했습니다.

## 2. 해결: 설치 → 판정 → 검사 → 측정

1. **설치.** `python bin/harness.py init`이 루트·영역 `AGENTS.md`, 플랜·리뷰·MR 양식과 Claude Code hooks를 생성합니다. `python bin/harness.py check`는 생성된 파일이 템플릿과 달라졌는지 검사합니다.
2. **작업 판정.** 영역별 규칙은 변경을 경량·표준·엄격으로 나눕니다. `python bin/harness.py judge`는 변경 파일의 경로 트리거를 읽어 판정을 제안하고, 문장으로 표현된 위험은 사람이 확인합니다.
3. **검사.** hooks는 보호 경로 편집을 차단하거나 확인을 요구하고, GitLab CI 조각은 MR 본문의 필수 절과 보안 검사를 확인합니다. GitHub용 CI 조각은 아직 제공하지 않습니다.
4. **측정.** 수집기는 병합 후 발견된 누락, 엄격 단계 비율, CI 실패 원인, 판정 불일치, hooks 개입을 주간 JSON·HTML 리포트로 만듭니다.

스택 프로필은 Spring Java, React TypeScript, Android Kotlin을 제공합니다. 단순히 파일 이름을 복사하는 데서 끝내지 않고, 생성 코드와 계층 규칙을 검사하는 방향으로 확장했습니다.

## 3. 검증: 빈 저장소에서 첫 MR까지

[리허설 기록](https://github.com/kiddo-psh/ai-dev-harness/blob/main/docs/rehearsal-m4-4.md)에 따르면, Spring 백엔드와 React 프론트엔드가 있는 빈 GitLab 프로젝트에 키트를 붙이고 첫날 체크리스트 1~9번을 64분에 수행했습니다. 이 시간에는 스택 골격 생성, 플랫폼 전환, Runner 등록, 사람 승인 대기가 포함됩니다. 일반 팀의 평균 도입 시간으로 볼 수는 없습니다.

엄격 단계 기능 두 건을 플랜, 구현, 분리 리뷰, MR 검사 순서로 진행했습니다. 첫 MR에서는 의존성 감사가 취약한 라이브러리 버전을 발견해 파이프라인을 실패시켰고, 두 번째 작업에서는 보호 경로의 SQL 파일 편집에 hooks가 사람 확인을 요구했습니다. 반면 Secret·SAST 검사의 자연 발생 검출은 없었고, 이미지 스캔은 대상 이미지가 없어 연결하지 않았습니다.

리허설에서 드러난 문제도 남겼습니다. Windows 줄끝과 실행 비트, 생성 문서의 포맷, 커밋 후 종료 검증의 누락처럼 실제 설치 과정에서 막힌 지점은 [후속 이슈](https://github.com/kiddo-psh/ai-dev-harness/issues)로 추적합니다.

## 4. 다음 검증

현재 확인한 것은 키트 자체 적용과 한 번의 빈 저장소 리허설입니다. 실제 팀 프로젝트에서 전 기간 사용하면서 이전 프로젝트와 **병합 후 누락, 절차 건너뛰기, hooks 개입**을 비교해야 방어 효과를 말할 수 있습니다. 전후 비교표는 아직 완성되지 않았습니다.
