## 각자의 에이전트가 다른 합의를 따르고 있었다

주차바로를 개발할 때 팀원 대부분이 AI 코딩 도구를 사용했습니다. 도구는 비슷했지만 사용하는 방식은 달랐습니다. 각자 이해한 요구와 판단을 전달했고, 어떤 작업은 사람끼리 합의하기 전에 구현부터 시작됐습니다. 서로 다른 합의를 전제로 개발하거나 코드 품질이 달라지는 일이 생겼습니다.

제게 크게 남은 문제는 팀원들이 같은 목표를 향해 개발한다는 느낌이 부족했다는 것입니다. 코드가 빨리 나와도 무엇을 만들지와 어떤 기준으로 받아들일지가 다르면 통합 과정에서 다시 맞춰야 했습니다.

다음 프로젝트인 feelm에서는 팀 공통 개발 규칙을 만드는 데 시간을 썼습니다. 요구사항과 계약의 우선순위, 구현 전에 합의할 항목, 변경 위험에 따른 플랜·리뷰와 검증 절차를 정리했습니다. 팀원들이 만족하며 사용하는 모습을 보면서 다음 팀에서도 재사용할 수 있게 만들고 싶었습니다.

## 재사용할 것은 개발 흐름이었다

feelm에서도 로컬에서는 통과하지만 CI에서는 실패하는 문제와 비효율적인 테스트가 남았습니다. 플랫폼과 기술 스택이 달라지면 검증 명령과 양식도 달라집니다. 규칙 문서만 복사하는 것으로는 이 차이를 다루기 어려웠습니다.

키트의 목표를 **새 저장소에 공통 절차를 설치하고, 실제 작업에서 적용 여부를 확인할 수 있게 하는 것**으로 잡았습니다. 사람이 판단할 위험과 도구가 검사할 조건을 나누고, 설치 → 작업 판정 → 검사 → 관측이 이어지도록 구성했습니다.

| 겪은 문제 | 키트의 대응 |
| --- | --- |
| 저장소마다 다른 규칙과 양식 | 설정에 따른 생성과 템플릿 이탈 검사 |
| 합의 전에 시작되는 구현 | 위험 단계에 따른 플랜·리뷰 절차 |
| 로컬과 CI의 다른 결과 | 영역 검증과 GitLab CI 조각 |
| 토큰 부족의 원인을 알기 어려움 | 세션·토큰·추정 비용 관측 |

## 결정 1. 원본과 적용 결과를 함께 관리하기

문서를 직접 복사해 수정하면 어느 부분이 의도적인 변경이고 어느 부분이 누락인지 알기 어렵습니다. 원본 템플릿과 저장소 설정을 두고 init으로 생성하며 check로 차이를 검사하도록 만들었습니다. 키트 자신에게도 같은 방식을 적용했습니다.

플랫폼·업무 추적 도구·영역별 검증 명령은 설정으로 받습니다. 팀마다 달라지는 값을 분리해 절차를 매번 다시 쓰는 일을 줄이려 했습니다. 다만 파일의 일치가 실제 절차 수행까지 증명하지는 않으므로 작업 중 제어와 병합 시 검사를 연결했습니다.

## 결정 2. 작업 중 제어를 병합 경계까지 연결하기

judge는 변경 경로로 위험 단계를 제안하고, Claude Code hooks는 보호 경로 편집을 차단하거나 확인을 요구합니다. GitLab CI 조각은 MR 본문, 영역 검증과 보안 검사를 수행합니다.

경로만으로 모든 위험을 판단할 수 없어 문장으로 표현된 위험은 사람이 확인합니다. 도구마다 hooks 지원도 다릅니다. 따라서 로컬 제어에 더해 병합 경계에서도 작업 근거를 검사하는 구성을 뒀습니다. 규칙에서 실행 가능한 조건을 골라 작업 흐름에 붙인 선택입니다.

## 규칙 적용 이후의 질문: 어디에 얼마나 쓰고 무엇을 검증했나

Claude Code 팀 플랜을 사용하면서 토큰 부족을 반복해서 겪었습니다. 어디에 사용량이 집중되는지 알아야 실행 방식도 바꿀 수 있었습니다. 이 필요에서 AgentOps를 추가했습니다.

처음에는 세션·토큰·추정 비용·hooks 개입을 수집하는 데서 시작했습니다. 이후 Claude Code와 Codex를 함께 사용하면서 서로 다른 원천을 어떻게 비교할지, 여러 작업을 오가는 세션을 어디에 귀속할지, 검증을 했다는 기록이 실제로 무엇을 보장하는지가 문제가 됐습니다.

현재는 로컬 대시보드와 OTel Collector → Prometheus·Loki → Grafana의 선택적 팀 관측 구성을 제공합니다. 기능을 크게 세 질문으로 나눴습니다.

| 화면 | 답하려는 질문 |
| --- | --- |
| 팀 사용량 | 사람·도구·모델별로 토큰과 추정 비용이 어디에 쓰였나? |
| 수집·차단 진단 | 기록이 들어오는가, 오류와 hooks 개입이 있었나? |
| 작업 검증 기록 | 어떤 작업에 어떤 검증·인수 조건·리뷰 근거가 연결됐나? |

아래 화면은 저장소가 공개한 **가상 팀원·목데이터 예시**입니다. 실제 팀의 비용이나 성과 수치는 아닙니다. 공통 사용량 화면은 v2 작업 버전, 작업 검증 기록은 별도 확장입니다.

![공통 v2 팀 사용량 화면. 가상 팀원과 목데이터로 토큰·추정 비용·미등록 단가를 표시한 예시](/images/projects/ai-dev-harness/team-usage.png)

## 결정 3. 두 도구의 사용량을 같은 계약으로 비교하기

Codex의 내장 텔레메트리와 키트가 읽는 세션 기록은 같은 사용량을 서로 다른 경로에서 관측합니다. 이를 합하면 중복이 생깁니다. 구독 계정의 내장 비용이 비어 있는 경우도 있고, 세션 누적 토큰을 매번 더하면 사용량이 부풀려집니다.

공통 텔레메트리 v2에서는 두 도구의 원천을 사용량·완료·전송 상태 사건으로 정규화했습니다. 청구 단위마다 안정적인 ID를 붙이고 공통 가격표와 사건 발생 시각으로 집계합니다. 내장 텔레메트리는 실시간 사용 여부를 보는 별도 원천으로 유지합니다.

| 설계 조건 | 처리 방식 |
| --- | --- |
| 스트리밍·재시도·다른 worktree에서의 중복 | 안정적인 기록 ID별 값을 집계하고 같은 사건은 다시 더하지 않음 |
| 가격표 변경 | 최초 전송 준비 시 단가·차원을 저장해 반복 전송에도 유지 |
| 단가 미등록 모델 | 토큰은 포함하고 비용은 부분 합계로 표시 |
| 늦게 도착한 사용량 | 전송일 대신 원래 사건의 KST 날짜에 귀속 |
| 전송 실패·부분 거절 | 네트워크 전 outbox에 저장하고 성공한 묶음만 완료 처리 |
| 검증 기록 없음·미지원 | 성공이나 0으로 채우지 않고 상태를 구분 |

이 선택은 합계만 예쁘게 보여주기보다 수치가 어떤 원천과 조건에서 만들어졌는지 설명하기 위한 것입니다. 예전 누적 형식의 로그와 7일을 넘겨 보내지 않은 기록에는 복원 한계가 있습니다. [공통 v2 계약](https://github.com/kiddo-psh/ai-dev-harness/blob/25cd3fd3d0a38ef34edd9d10853bc27ddf6cebef/docs/telemetry-v2.md)에 지원 범위와 상태 해석을 남겼습니다.

## 결정 4. 작업 완료 주장에 실행 근거를 연결하기

사용량만으로는 작업이 검증됐는지 알 수 없습니다. 실행 근거 수집 확장에서는 세션을 작업·PR·역할에 연결하고 검증, 사람의 개입, 질문 대기, 리뷰 처리 상태를 별도 사건으로 기록합니다.

세션이 작업을 옮겼다면 늦게 수집된 사건도 발생 당시의 작업에 귀속해야 합니다. 연결 이력을 시간 구간으로 보존하고, 자동 연결은 사용자가 활성화한 이후의 같은 worktree 새 세션에만 적용했습니다. 연결 전 기록을 현재 작업의 성과로 자동 소급하지 않습니다.

검증 실행은 실행 ID와 전후 코드 상태 해시를 남깁니다. 실행 중 코드가 바뀌면 통과로 기록하지 않고, 인수 조건의 검증 수는 같은 작업의 관측된 통과 실행과 상태 해시가 연결된 경우에만 증가시킵니다. 테스트 하나의 통과를 작업 전체 완료로 승격하지 않는 방식입니다.

정형 질문과 답변은 대기 구간으로 연결하지만 일반 답변 문구에서 승인·거절을 추정하지 않습니다. 리뷰의 채택 역시 수정 완료나 검증 통과와 구분합니다. 직접 관측·사람 신고·에이전트 신고의 출처를 표시하고, 기본 수집에서는 프롬프트·응답·코드 원문을 중앙으로 보내지 않습니다.

![작업 검증 기록 화면. 예시 작업의 검증과 인수 조건, 리뷰 사건을 보여주는 목데이터](/images/projects/ai-dev-harness/task-evidence.png)

## 결정 5. 반복 수집 대신 완료 이벤트에서 수집하기

꾸기에 적용하면서 운영 방식도 바꿨습니다. 30초 주기 수집은 제거하고 완료 이벤트·PR 요약·수동 실행 시 한 번 수집한 뒤 종료하게 했습니다. 변화가 없으면 전송하지 않으며 실패 기록은 다음 이벤트에서 재시도합니다. Windows에서는 백그라운드 작업이 콘솔 창을 띄우지 않도록 처리했습니다.

두 확장의 계기는 다릅니다. 공통 v2는 Claude Code의 SessionEnd와 Codex Stop hook을 사용하며 Codex 전송에는 간격을 둡니다. 실행 근거 확장은 선택 설치한 Codex 완료 notify, Claude 관측 Stop, PR 요약에서 수집합니다. 이를 같은 상시 수집기로 설명하지 않습니다.

Codex 비대화형 실행에서 프로젝트 hook이 동작하지 않는 등 환경별 한계도 남아 있습니다. 자동 수집이 모든 실행 환경을 덮는다고 가정하지 않고 수동 실행과 수집 상태 진단을 제공합니다.

![수집·차단 진단 화면. 가상 팀원의 수신 상태와 오류·hooks 개입을 나타낸 목데이터](/images/projects/ai-dev-harness/collection-diagnostics.png)
