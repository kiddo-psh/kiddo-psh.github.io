식단을 기록한 날과 운동만 기록한 날에 같은 분석이 필요할까요? 기록이 하나도 없는 주에도 AI가 코칭 문장을 만들어야 할까요?

냠냠코치는 사진 식단 분석, AI 영양 상담, 주간 코칭을 제공하는 LLM/VLM 기반 건강 코칭 서비스입니다. 저는 2인 팀의 팀장으로 Backend와 AI 서버를 맡아 운동 루틴과 프로그램, 주간 리포트, 영양 상담과 홈 코멘트를 구현했습니다.

이 글은 두 부분으로 나뉩니다. 앞부분은 사진 분석 방식의 근거를 직접 만든 평가셋으로 검증한 과정이고, 뒷부분은 기록에 따라 필요한 분석만 실행하도록 주간 코칭 흐름을 바꾼 과정입니다. 원 프로젝트의 기능 구현과 이후에 진행한 개선은 구분해 설명합니다.

## 측정된 적 없는 설계 근거를 평가셋으로 쟀다

사진 식단 분석은 VLM이 사진에서 음식명·그램·kcal을 직접 추정하는 방식이었습니다. 이 방식을 고른 근거는 “DB 조회 대신 VLM이 직접 추정해도 정확도 차이가 없다”였지만, 한 번도 잰 적이 없었습니다.

그래서 저울 실측과 포장 영양표시로 정답을 단 **실제 사진 31장 평가셋**과 평가 하니스를 직접 만들었습니다. 채점 도구부터 검증해 결함 4건을 고쳤고, 그중 1건은 판정을 뒤집었습니다.

kcal 오차만 보면 그램 추정 오차와 kcal/g 계수 오차가 서로 상쇄될 수 있어, kcal 오차를 그램 오차와 밀도 오차로 나눠 봤습니다. DB 조회 방식은 현실적인 매칭 규칙과, 매칭이 항상 성공한다고 가정한 도달 불가 상한(oracle) 두 가지로 같은 사진에 비교했습니다.

| 확인한 것 | 결과 |
| --- | --- |
| DB 음식명 매칭 실패율 | 37.5% |
| 매칭을 느슨하게 했을 때 kcal MAPE | 21.2% → 46.8% (악화) |

DB의 영양 계수 자체는 정확했지만, 사진에서 나온 이름을 DB 레코드에 매칭하는 단계에서 우위가 사라졌습니다. 결정은 유지하되 **결론의 근거를 “정확도 차이가 없다”에서 “이름 → 레코드 매칭이 불가능하다”로 수정**하고, 설계 문서에 정정 기록을 남겼습니다.

## 질문 밖에서 과검출을 찾았다

평가하던 중 합계 kcal이 과대 추정 쪽으로 쏠리는 것을 발견했습니다. 원인은 요리명과 구성 재료를 함께 출력하는 과검출이었습니다. 예를 들어 “가츠동”과 함께 “계란, 홍생강, 파”를 나열해 같은 음식을 두 번 셌습니다.

요리와 구성 재료를 함께 나열하지 말라는 제약 한 줄만 다른 대조 프롬프트로 비교했습니다.

| 지표 | 제약 추가 전 | 제약 추가 후 |
| --- | --- | --- |
| 과검출 | 49건 | 7건 |
| 음식명 F1 | 0.38 | 0.77 |
| 항목 kcal MAPE | 34.1% | 20.8% |

나빠진 지표는 없었고, 기존 프롬프트는 대조군으로 보존한 채 서비스에 반영했습니다. 다만 평가셋이 31장이고 짝지은 비교 표본이 작아, 실행 간 분산을 분리하는 반복 측정이 남아 있습니다. 이 채점기는 리뉴얼 프로젝트 [꾸기](/projects/kkugi)의 분류기 평가에도 그대로 이식했습니다.

## 운동만 기록했는데 영양 분석도 실행되고 있었다

주간 코칭은 영양·운동·목표를 각각 분석한 뒤 결과를 합치는 구조였습니다. 여기서 Agent는 한 분야의 분석을 담당하는 AI 실행 단계입니다. 전문 분석 세 단계와 결과를 종합하는 단계까지 모두 실행하면 네 단계가 됩니다.

리포트 성능 테스트 중 예상보다 많은 토큰이 사용되는 것을 보고 호출 흐름을 확인했습니다. 기존 방식은 사용자의 기록 상태와 관계없이 모든 단계를 실행했습니다. 운동만 기록한 요청에도 영양 분석이 돌고, 분석할 자료가 없는 분야까지 결과에 포함될 수 있었습니다.

먼저 정해야 할 것은 **얼마나 좋은 문장을 만들지에 앞서, 이번 요청에 어떤 분석이 필요한지**였습니다.

## 기록을 확인한 뒤 필요한 분석만 실행하도록 바꿨다

Spring Boot가 사용자 기록을 모으고, FastAPI가 AI 분석을 실행해 화면으로 코칭을 전달합니다. 변경한 구조에서는 기록과 분석 사이에 실행 단계를 고르는 규칙을 뒀습니다.

영양 기록이 있으면 영양 분석을, 운동 기록이 있으면 운동 분석을 선택합니다. 선택할 전문 분석이 없으면 결과를 종합하는 AI 호출도 생략하고 정해진 안내를 반환합니다.

## 분석 순서를 고르는 일에 AI를 한 번 더 부를 필요가 있을까?

어떤 분석을 실행할지 다른 LLM이 결정하는 Supervisor도 설계 대안으로 검토했습니다. 다만 당시에는 시나리오가 제한적이라고 봤고, 선택 자체에 추가 토큰을 사용하는 점도 고려했습니다. 이미 구조화된 기록에서 판단할 수 있는 조건은 코드의 규칙으로 표현했습니다.

| 입력에서 확인하는 내용 | 실행할 분석 |
| --- | --- |
| 유효한 영양 기록이 있는가? | 영양 분석 |
| 유효한 운동 세트가 있는가? | 운동 분석 |
| 체중 추세를 계산할 수 있거나 영양·운동 분석이 모두 필요한가? | 목표 분석 |
| 전문 분석을 하나도 선택하지 않았는가? | 종합 생성 없이 고정 안내 |

입력에서 확인한 사실과 실행 선택을 분리하고, 선택·생략한 단계와 이유 코드를 남겼습니다. 같은 기록을 넣었을 때 같은 경로를 선택하는지 테스트할 수 있게 했습니다.

Supervisor를 실제로 구현해 규칙과 비교 실험한 것은 아닙니다. 자유로운 질문의 의도를 해석하거나 분석 종류가 크게 늘어난다면 규칙만으로 충분한지 다시 판단해야 합니다. 이번 선택은 현재 입력에서 명시적으로 판단할 수 있는 범위에 맞춘 것입니다.

## 영양 분석을 한다고 매번 식품을 검색할 필요는 없었다

영양 목표를 얼마나 달성했는지 요약하는 일과, 부족한 영양소를 보충할 식품을 추천하는 일은 필요한 근거가 다릅니다. 기존에는 영양 분석을 실행하면 항상 외부 지식을 검색했습니다.

검색한 문서를 AI 답변의 근거로 사용하는 방식을 RAG라고 합니다. 저는 이 검색을 영양소 부족 조건에 따라 선택하도록 바꿨습니다.

비교 가능한 영양소 달성률 중 하나라도 80% 미만이면 가장 부족한 영양소를 중심으로 검색합니다. 목표가 0인 항목은 비교에서 제외하고, 최대 3개 문서 중 검색 거리 기준을 통과한 결과만 사용합니다. 검색에 실패하거나 결과가 비어 있으면 근거를 확보하지 못한 상태로 처리합니다.

이 조건은 불필요한 검색과 관련성이 낮은 문서의 유입을 통제하기 위한 구현 규칙입니다. 80%와 검색 거리 기준이 최적이라고 입증한 것은 아니며, 데이터와 검색 모델이 바뀌면 다시 확인해야 합니다.

## 분석 호출은 줄었지만 코칭 품질까지 좋아졌다고 할 수는 없다

고정 입력 8개를 같은 비중으로 비교한 기록에서 평균 실행 Agent 수는 4.0개에서 2.5개로 줄었습니다. 이 입력은 실행 선택을 확인하기 위한 평가용 사례이며, 실제 사용자의 요청 분포나 서비스의 모든 상황을 대표하지 않습니다.

당시 응답시간과 비용도 기록했지만, 효과를 해석하는 데 제약이 있습니다.

| 측정 기록 | 결과 | 함께 봐야 할 조건 |
| --- | --- | --- |
| 평균 응답시간 | 11.104초 → 8.673초 | 입력별 3회 표본이며 기준선 프롬프트가 다름 |
| p90 응답시간 | 12.281초 → 12.235초 | 느린 요청의 변화는 작았음 |
| 요청당 비용 | $0.004276 → $0.004094 | 임베딩 의존성 누락으로 검색이 대체 경로로 동작 |

현재 확인할 수 있는 핵심 변화는 **기록에 따라 실행 단계를 선택하게 됐다는 것**입니다. 지연과 비용의 개선 효과는 프롬프트·모델 설정을 맞추고 검색이 정상 동작하는 환경에서 다시 측정해야 합니다.

## 어떤 호출에 시간과 토큰이 쓰였는지 남겼다

실행 단계를 생략할 수 있게 바꾸면, 실제 요청이 어떤 경로를 거쳤는지도 확인할 수 있어야 합니다. Claude 호출의 지연·입출력 토큰·추정 비용을 기록하고 실행 ID로 묶는 계측을 추가했습니다.

홈 AI 코멘트에서는 DB 읽기부터 Redis 조회와 외부 AI 호출까지 감싸던 트랜잭션 범위도 줄였습니다. 외부 응답을 기다리는 시간이 DB 연결 점유로 이어질 수 있었기 때문입니다. 이 변경이 실제 부하에 미친 효과는 별도로 실험하지 않았습니다.

이번 개선에서는 기록에 맞춰 분석 범위를 통제하고 그 선택을 검사할 수 있게 만들었습니다. 다음에는 같은 조건에서 응답시간과 비용을 다시 측정하고, 기록과 맞지 않는 조언·근거 없는 수치·빠진 분석을 출력 평가에 포함해야 합니다.

호출이 줄었다는 사실만으로 코칭이 좋아졌다고 판단할 수는 없습니다. 줄인 단계가 사용자가 필요로 하던 분석은 아니었는지까지 확인하는 것이 다음 과제입니다.
