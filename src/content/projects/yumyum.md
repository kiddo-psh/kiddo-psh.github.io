## 예상보다 많은 토큰에서 시작한 조사

주간 코칭은 영양·운동·목표 Agent가 기록을 분석하고 Synthesis가 결과를 합치는 구조였습니다. 리포트 분석 성능 테스트 중 예상보다 많은 토큰이 사용되는 것을 보고 호출 흐름을 확인했습니다.

고정된 흐름은 요청마다 모든 Agent를 실행했습니다. 운동만 기록한 요청에도 영양 분석이 돌고, 분석할 기록이 없는 분야까지 결과에 포함될 수 있었습니다. 먼저 해결할 문제는 **이 요청에 어떤 분석이 필요한지**였습니다.

## 기록과 분석 사이에 실행 결정을 두기

Spring Boot가 사용자 기록을 모으고 FastAPI가 분석해 화면에 코칭을 전달합니다. 원 프로젝트의 4주 동안은 서비스 기능을 구현했고, 9월에는 기록과 분석 사이의 실행 결정을 개선했습니다.

기존에는 모든 분석을 실행한 뒤 합쳤습니다. 변경한 흐름은 기록을 먼저 확인하고 필요한 전문 Agent만 실행합니다. 분석할 기록이 없으면 종합 생성도 생략하고 정해진 안내를 반환합니다.

![기록에 따라 필요한 Agent를 선택하는 흐름](/images/projects/yumyum/01-routing.svg)

## 결정 1. 실행 선택을 규칙으로 표현하기

LLM Supervisor도 설계 대안으로 검토했습니다. 당시에는 다룰 시나리오가 제한적이라고 보았고 선택을 위한 추가 토큰 사용도 고려했습니다. 구조화된 기록으로 판단할 수 있는 범위를 규칙으로 구현했습니다. Supervisor를 실제 구현해 비교 실험한 것은 아닙니다.

| 확인한 사실 | 실행할 분석 |
| --- | --- |
| 유효한 영양 기록 존재 | 영양 Agent |
| 유효한 운동 세트 존재 | 운동 Agent |
| 체중 추세 계산 가능 또는 영양·운동 모두 선택 | 목표 Agent |
| 전문 Agent가 하나도 선택되지 않음 | 종합 생성 생략, 고정 안내 반환 |

입력에서 계산한 사실과 선택 결과를 분리하고 선택·생략한 Agent 및 이유 코드를 남겼습니다. 같은 입력에 같은 선택을 하는지 테스트할 수 있습니다. 자유로운 질문의 의도까지 해석해야 한다면 규칙만으로 충분한지는 다시 판단해야 합니다.

## 결정 2. 영양 분석과 식품 검색의 필요를 구분하기

달성률 요약과 부족한 영양소를 보충할 식품 제안은 필요한 근거가 다릅니다. 영양 Agent가 실행될 때 항상 검색하던 방식을 바꿨습니다.

비교 가능한 영양소 달성률 중 하나라도 80% 미만이면 가장 부족한 영양소를 중심으로 검색합니다. 목표가 0인 항목은 비교에서 제외하고 최대 3개 문서 중 거리 기준을 통과한 결과만 사용합니다. 검색 실패나 빈 결과는 근거가 없는 상태로 처리합니다. 임계값은 현재 구현의 설정이며 데이터와 검색 모델이 바뀌면 재검증해야 합니다.

이는 불필요한 검색과 관련성이 약한 근거의 유입을 통제하려는 선택입니다. 실제 코칭 품질은 출력 평가로 확인해야 합니다.

## 평가로 확인한 변화와 다시 측정해야 할 것

고정 입력 8개에 같은 비중을 주어 실행 경로를 비교한 기록에서 평균 실행 Agent가 4.0개에서 2.5개로 감소했습니다. 이 입력들은 평가용이며 서비스의 모든 시나리오나 실제 요청 분포를 의미하지 않습니다.

![평가 입력 8개의 Agent 실행 조합](/images/projects/yumyum/02-fixture-matrix.svg)

| 항목 | 기존 계측 기록 | 비교의 한계 |
| --- | --- | --- |
| 평균 응답시간 | 11.104초 → 8.673초 | 입력별 3회 표본, 기준선 프롬프트 차이 |
| p90 응답시간 | 12.281초 → 12.235초 | 느린 요청의 변화는 작았음 |
| 요청당 비용 | $0.004276 → $0.004094 | 임베딩 의존성 누락으로 RAG가 fallback 상태 |

현재 설명할 수 있는 핵심 변화는 실행 경로입니다. 지연·비용 효과는 프롬프트와 모델 설정을 맞추고 검색이 정상 동작하는 환경에서 다시 측정해야 합니다.

## 실행 흐름을 바꾼 뒤에는 관측이 필요했다

Claude 호출의 지연·입출력 토큰·비용을 기록하고 실행 ID로 묶는 계측을 추가했습니다. 어떤 단계에서 자원이 쓰이는지 추적하기 위한 작업입니다.

홈 AI 코멘트에서는 DB 읽기부터 Redis 조회와 외부 AI 호출까지 감싸던 트랜잭션 범위를 줄였습니다. 외부 응답 대기가 DB 연결 점유로 이어질 수 있었기 때문입니다. 이 변경의 부하 효과는 별도 실험하지 않았습니다.

## 결과와 다음 판단

원 프로젝트는 SSAFY 1학기 관통 프로젝트 최우수상(부울경 4반 1등)을 수상했습니다. 이후 라우팅 개선과 수상 시점은 구분합니다.

![관통 프로젝트 최우수상 증빙](/images/projects/yumyum/award.png)

이번 개선에서는 기록에 맞춰 분석 범위를 통제하는 구조와 그 선택을 검사하는 경로를 만들었습니다. 다음에는 동일 조건의 재계측과 함께 기록에 맞지 않는 조언·근거 없는 수치·빠진 분석을 출력 평가에 포함해야 합니다. 호출 감소가 유용한 코칭의 유지로 이어지는지 확인하는 단계입니다.
