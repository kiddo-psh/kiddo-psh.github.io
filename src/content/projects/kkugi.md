식단 기록 앱은 입력이 번거로워 사흘을 넘기기 어렵습니다. 웨이트 기록은 더 심합니다. 운동명을 검색하고, 세트를 추가하고, 무게와 횟수를 입력하는 일을 폰을 들었다 놨다 하며 반복해야 합니다.

꾸기는 이 입력을 줄이려는 프로젝트입니다. 저는 팀장으로 저장소의 협업 규칙을 만들고, 음식 사진을 인식하는 모델의 학습·평가·서빙을 맡았습니다.

이 글에서는 모델의 정확도 숫자를 서비스가 믿을 수 있는 기준으로 바꾸기 위해 무엇을 측정했는지, 6명이 AI 코딩 도구와 함께 일하는 방식을 어떻게 정했는지 정리합니다.

## 기록이 목적이 되면 습관이 끊긴다

꾸기는 2026년 6월에 2명이 4주 동안 만든 웹 서비스 [냠냠코치](/projects/yumyum)(v1)를 다시 개발한 프로젝트입니다. v1에서는 텍스트로 음식을 검색해 고르고, 운동은 폰의 입력 폼으로 기록했습니다. 기록 자체가 일이 되는 구조였습니다.

리뉴얼에서는 **앱이 먼저 제시하고, 사용자는 확인하거나 살짝 고친다**는 원칙을 세웠습니다. 식사는 사진을 찍으면 인식 결과가 카드로 나오고, 틀린 부분만 고칩니다. 운동은 헬스장에서 폰을 사물함에 두고 워치만 찬다는 상황을 전제로, 전날 폰이 내려 둔 루틴을 워치에서 한 번 탭해 세트를 완료합니다.

팀은 이 원칙을 측정할 수 있는 기준으로 적었습니다.

| 기준 | 목표 |
| --- | --- |
| 앱 실행 → 운동 시작 | 3탭 이하 |
| 세트 완료 | 워치 1탭 이하 |
| 촬영 → 식사 저장 | 3탭 이하 (촬영·확인·저장) |
| 네트워크 없는 운동 기록 | 워치·폰 모두 가능 |

## 사용자의 수정 한 번이 다음 모델이 되는 구조

폰과 웹은 Spring만 호출합니다. 음식 인식과 Claude 코칭을 맡는 FastAPI 추론 서버는 Spring의 내부 호출만 받고 외부에 열지 않습니다. 워치는 서버와 인증을 모르고, 폰과 Data Layer로만 루틴과 세션을 주고받습니다.

식사 기록은 모델의 예측(`prediction`)과 사용자가 확정한 값(`correction`)을 모두 저장합니다. 이 쌍이 다음 학습의 원료가 됩니다. 제가 맡은 부분은 이 고리의 뒤쪽 절반, 곧 데이터셋을 만들고 모델을 학습·평가해 서빙까지 연결하는 일입니다.

## 모델을 고르기 전에 잣대부터 옮겼다

처음 결정해야 했던 것은 음식 인식 방식이었습니다. 후보는 v1처럼 Claude Vision이 이름·그램·kcal을 한 번에 추정하는 방식과, 사전학습 분류기를 fine-tune하는 방식이었습니다. 두 방식을 비교하려면 같은 잣대가 필요했습니다.

그래서 v1의 정확도 채점기를 모델과 무관한 형태로 이식했습니다. 정답 라벨과 예측 JSONL만 받아 음식명 정밀도·재현율·F1, 그램과 kcal의 평균 절대 백분율 오차(MAPE)를 계산합니다. v1의 원시 예측을 다시 채점해 v1 결과와 같은 값이 나오는 것을 먼저 확인했습니다.

이식하면서 v1 실험에서 얻은 두 가지 교훈도 함께 옮겼습니다.

첫째, kcal 오차만 보면 안 됩니다. 그램 추정 오차와 kcal/g 계수 오차가 서로 반대 방향이면 상쇄되어 kcal 오차가 작아 보입니다. 그래서 그램 오차를 소거한 밀도(kcal/g) MAPE를 따로 계산합니다. v1에서 프롬프트를 고친 뒤에는 밀도 오차(22.36%)가 그램 오차(19.04%)보다 컸습니다. "오차의 주원인은 그램 추정"이라는 처음 가정이 성립하지 않았던 것입니다.

둘째, 모델 출력의 구조가 정확도를 크게 바꿉니다. v1의 Vision 모델은 "가츠동"과 함께 "돈카츠, 계란, 흰쌀밥"을 나열해 합계 kcal이 정답의 1.97배가 되곤 했습니다. 요리와 구성 재료를 함께 나열하지 말라는 규칙 하나로 결과가 다음처럼 바뀌었습니다.

| 지표 | 규칙 추가 전 | 규칙 추가 후 |
| --- | --- | --- |
| 음식명 F1 | 0.377 | 0.773 |
| 정밀도 | 0.246 | 0.708 |
| 과검출 | 49건 | 7건 |

이 수치는 v1 평가셋 31장에서 나온 기준선입니다. 리뉴얼의 분류기는 이 채점기로 같은 기준에서 비교하도록 했습니다. 다만 v1 평가셋에는 상품 사진이 섞여 있어 저장소에 넣지 않고, 실사용 사진 평가셋은 팀이 직접 찍은 사진으로 따로 모으기로 했습니다.

## 87%는 어떤 사진에서 나온 숫자인가

베이스 모델은 ImageNet 사전학습 분류기를 fine-tune하는 쪽으로 정했습니다. 400종 전체를 돌리기 전에 AI Hub 74번 음식 데이터셋의 50종 부분집합으로 모델과 입력 해상도를 먼저 비교했습니다.

| 실험 | 모델 | 입력 | test top-1 | test top-5 | 학습 시간 |
| --- | --- | --- | --- | --- | --- |
| 50종 | ConvNeXt-T | 224 | 93.2% | 98.1% | 4분 |
| 50종 | ConvNeXt-T | 384 | **94.7%** | 97.9% | 9분 |
| 50종 | EfficientNet-B0 | 224 | 88.4% | 96.7% | 4분 |
| 50종 | EfficientNet-B0 | 384 | 91.5% | 97.1% | 17분 |
| 400종 본 학습 | ConvNeXt-T | 384 | **84.3%** | 94.4% | 161분 |
| 400종 재학습 | ConvNeXt-T | 384 | 84.3% | 94.4% | 150분 |

ConvNeXt-T 384px는 224px보다 1.5%p, EfficientNet-B0보다 3~6%p 높았습니다. 512px는 얻는 정확도에 비해 비용이 커서 시도하지 않았습니다. 학습은 노트북 GPU(RTX 4070 Laptop 8GB)에서 돌렸고, 같은 시드로 다시 학습했을 때 완전히 같은 값이 나오는 것을 확인했습니다.

본 학습은 한 번 실패했습니다. 라벨에 높이가 0인 상자가 섞여 있었기 때문입니다. 너비나 높이가 8px 미만인 상자는 라벨 오류로 보고, 학습할 때 전체 사진으로 대체하는 규칙을 넣은 뒤 다시 돌렸습니다.

400종 모델의 혼동 상위 쌍을 보니 깻잎장아찌와 깻잎김치, 순대국밥과 순대국처럼 사실상 같은 음식의 이름 차이가 많았습니다. 모델의 문제가 아니라 클래스 체계의 문제였습니다. 이름만 다른 같은 음식 4쌍을 병합해 396종으로 줄였고, 영양이 다른 비슷한 음식은 합치지 않았습니다.

이후에는 원본 사진에 EXIF 회전 정보가 있는데 이를 반영하지 않아, 회전된 사진에서 라벨 상자 좌표가 실제 음식 위치와 어긋난다는 것을 발견했습니다. EXIF를 먼저 반영하고 원본 XML에서 상자를 다시 계산한 v3 데이터셋으로 재학습했습니다.

| 평가 | v2 (EXIF 미반영) | v3 (EXIF 교정) |
| --- | --- | --- |
| AI Hub 평가 분할 7,994장, 상자 크롭 top-1 | 87.17% | 87.19% |
| 웰스토리 식당 사진 26장, 상자 크롭 top-1 | 6장 | 8장 |
| 웰스토리 식당 사진 26장, 전체 사진 top-1 | 4장 | 2장 |

교정은 데이터의 오류를 바로잡은 일이지만, 정확도가 크게 좋아졌다고 해석하지 않았습니다. AI Hub 평가에서는 차이가 0.02%p였고, 실사용 사진에서는 방향이 엇갈렸습니다. 400종 첫 학습의 84.3%와 이 표의 87%도 직접 비교하지 않습니다. 클래스 수가 다르고 평가 사진의 상자 좌표도 교정됐기 때문에, 그 차이를 병합 효과 하나로 설명할 수 없습니다.

더 중요한 것은 위 표의 위아래 차이였습니다. **87%는 라벨 상자로 음식만 잘라낸 사진에서 나온 숫자입니다.** 실제 사용자의 폰 사진에는 상자가 없으므로 전체 사진이 모델에 들어갑니다. 웰스토리 식당에서 찍은 사진 50장 중 학습 클래스에 대응하는 26장만 골라 전체 사진으로 넣었을 때 top-1은 2장이었습니다. 나머지 24장은 미지원 음식이거나 대응이 확정되지 않아 분모에서 뺐으므로, 실제 서비스 조건은 이보다 더 불리합니다.

이 결과를 보고 두 가지를 정했습니다.

- 학습 결과(`result.json`)에 "test top-1은 크롭 기준"이라는 조건을 명시하고, 평가 스크립트는 크롭 조건과 전체 사진 조건을 모두 재도록 했습니다. 실사용 사진은 학습 클래스 안과 밖을 나눠 F1을 따로 내고, "클래스 밖인데 확신도 0.5 이상"인 사진 목록을 남깁니다.
- 추론 서버는 정답 하나 대신 후보 목록과 확신도를 돌려주고, 사용자가 고르거나 고치게 했습니다. 정확도가 낮아도 수정 흐름으로 제품이 성립하고, 그 수정이 다음 학습 데이터가 되게 하는 것이 처음 기획의 의도였습니다. 미지원 음식은 확신도만으로 판정하지 않습니다.

## 새 모델이 더 낫다는 것은 누가 판단하나

수정 데이터로 재학습하는 고리를 만들면, 새 모델이 실제로 나아졌는지 판단할 기준이 필요합니다. 품질 게이트는 다음 규칙으로 만들었습니다.

| 조건 | 결과 |
| --- | --- |
| 새 모델 top-1 ≥ 현재 Production 모델 top-1 | 통과 → Staging 등록 |
| 두 모델의 평가 데이터 버전이 다름 | 실패 (비교 불가) |
| 현재 Production 모델이 없음 | 통과 (첫 등록) |

**평가 데이터가 다르면 숫자를 비교하지 않게 한 것이 핵심입니다.** 이를 위해 데이터셋 분할을 결정적으로 만들었습니다. 클래스 안에서 세트 ID를 해시 순으로 늘어놓고 80/10/10으로 자르며, 같은 음식을 다른 각도에서 찍은 사진은 항상 같은 분할에 넣습니다. 다음 버전은 이전 버전의 분할 파일을 그대로 이어받습니다. 실제로 v2와 v3의 클래스·분할 파일이 바이트 단위로 같은지를 테스트로 확인했습니다.

게이트를 통과해도 Production 승격은 사람이 승인합니다. 학습과 서빙 사이의 어긋남도 막았습니다. 학습은 모델(`model.onnx`)과 함께 서빙이 따라야 할 전처리 값(`preprocess.json`: 입력 크기, 리사이즈 비율, 정규화 상수, EXIF 정책)을 남기고, 추론 서버와 평가 스크립트는 같은 런타임으로 이 파일만 읽습니다. 학습 설정과 EXIF 정책이 다르면 학습이 멈추도록 했습니다.

## 6명이 AI 에이전트와 같은 저장소에서 일하는 규칙

팀원 모두가 Claude Code나 Codex로 작업했습니다. 저는 저장소 규칙 담당으로, AI가 만든 변경을 사람이 리뷰할 수 있게 하는 절차를 정했습니다. 이 절차는 제가 따로 만든 [AI 개발 하네스 키트](/projects/ai-dev-harness)(ai-dev-harness)로 저장소에 적용했습니다. 키트는 설정 파일(`harness.json`) 하나에서 영역별 검증 명령, 판정 트리거, 아키텍처 규칙 테스트, hooks, MR 템플릿을 만들어 냅니다. 프로젝트 기간 중에도 팀의 사용 경험을 반영해 0.3.0에서 0.4.0까지 올렸습니다.

모든 변경은 닿는 범위에 따라 세 단계로 판정합니다.

| 판정 | 조건 | 산출물 |
| --- | --- | --- |
| 경량 | 문서·주석, 또는 동작을 바꾸지 않는 테스트만 변경 | 영역 검증만 |
| 표준 | 아래 트리거에 해당하지 않음 | 플랜과 리뷰 1회 |
| 엄격 | API 계약, DB 마이그레이션, 공통 규약, 인프라, 의존성 등을 변경 | 사람의 플랜 승인 + 독립 리뷰 2회 |

엄격 판정의 리뷰는 구현과 다른 두 세션이 플랜, diff, 기준 문서만 보고 따로 수행합니다. 두 리뷰는 서로의 결과를 읽지 않고, AI가 합집합 대조표를 만든 뒤 사람은 의견이 갈리는 항목만 판단합니다. 같은 맥락을 본 리뷰어가 같은 결함을 놓치는 일을 줄이려는 장치입니다. 리뷰 결과 파일은 MR과 함께 커밋해 지금까지 30건이 저장소에 남아 있습니다.

제 작업도 같은 절차를 거쳤습니다. 분류기 학습 MR은 학습 의존성(torch, timm, onnx 등)을 새로 추가해 엄격으로 판정됐습니다. 구현과 분리된 두 리뷰 세션이 각각 5건과 6건의 발견 사항을 냈고, 합집합 9묶음 중 7개를 반영했습니다. 설정 파일의 오타 키가 조용히 기본값으로 돌지 않게 막는 검증, 서빙이 따라야 할 전처리 값의 기록, ONNX 출력을 배치 2 입력으로 검증하는 일이 이때 들어갔습니다. 전체 사진 기준 평가처럼 범위가 큰 2개는 다음 업무로 넘겼습니다.

추론 서버 MR의 리뷰에서는 1×N처럼 극단적인 비율의 이미지가 몇 KB만으로도 리사이즈 단계에서 CPU와 메모리를 크게 쓸 수 있다는 지적이 나와, 디코드 직후 치수를 거르도록 고쳤습니다.

규칙을 문서로만 두지 않고 로컬 hooks와 MR 본문 검사로 확인하게 했습니다. 엄격 변경은 플랜에 사람의 승인이 적혀야 구현을 시작할 수 있고, MR 본문에는 판정, 리뷰 결과, 에이전트 기록(세션·토큰·추정 비용)이 들어가야 합니다.

### 공유 계정에서 누가 얼마나 썼는지

MR 본문의 기록은 병합된 뒤에야 모입니다. 작업 중의 사용량과 도구 허용·거부, hooks 개입을 한 화면에서 보려면 팀원 PC의 텔레메트리를 모아야 했습니다. 문제는 Claude Team 계정 2개를 3명씩 함께 쓰고 있어, 도구가 붙이는 계정 정보로는 사람을 구분할 수 없다는 점이었습니다.

관측 서버 앞에 TLS와 팀원별 토큰을 검사하는 수신 지점(Caddy)을 두고, 토큰으로 팀원 이름을 정해 OTel Collector에 넘기게 했습니다. 클라이언트가 보낸 이름은 쓰지 않습니다. SSH 터널이나 IP 허용 목록도 검토했지만, 팀원의 위치가 정해져 있지 않고 같은 IP 뒤의 사람을 구분하지 못해 택하지 않았습니다.

설계 중에 Loki의 제약도 발견했습니다. Loki는 한 로그 스트림의 가장 새 줄보다 1시간 넘게 오래된 줄을 버립니다. 팀원 모두의 기록이 한 스트림에 섞이면 늦게 보낸 기록이 조용히 사라집니다. 그래서 레이블 규칙에 예외를 두고 세션 ID로 스트림을 나눴습니다. 한 세션 안에서 1시간 넘게 늦은 기록은 여전히 버려질 수 있다는 한계는 결정 기록에 남겼습니다.

## 재시도 수치는 시뮬레이션으로 먼저 비교했다

API 규약의 클라이언트 재시도 규칙도 근거 없이 정해져 있었습니다. 서버가 잠깐 멈췄다 돌아올 때 모든 클라이언트가 같은 간격으로 다시 보내면 복구 직후 서버가 다시 무너질 수 있습니다.

클라이언트 300개, 10초 장애, 초당 50건을 처리하는 서버, 최대 6회 시도 조건으로 정책을 비교하는 시뮬레이션을 만들었습니다.

| 정책 | 복구 직후 순간 요청량 (처리 한도 대비) | 최종 성공률 |
| --- | --- | --- |
| 지터 없는 지수 백오프 | 약 11배 | 34% |
| full jitter 지수 백오프 | 약 1.7배 | 85% |

full jitter의 p95 대기는 22초였습니다. 화면에서 기다리는 사용자에게는 너무 긴 시간입니다. 그래서 재시도 규칙을 둘로 나눴습니다.

- **화면 요청**은 최대 3회, 5초가 지나면 새 재시도를 멈추고 안내를 보입니다.
- **백그라운드 전송**(워치에서 올라온 운동 세션 등)은 30초에서 시작해 최대 30분 간격으로 횟수 제한 없이 다시 보냅니다. 같은 세션을 여러 번 보내도 클라이언트 UUID로 중복 저장되지 않으므로 계속 보내도 안전합니다.

이 수치는 아직 가정입니다. 실제 배포 중 장애 길이와 응답 시간 p99를 잰 뒤에 확정하기로 하고, 규약 문서의 각 수치에 가정 표시를 남겼습니다.

## 지금까지 확인한 것과 아직 확인하지 못한 것

프로젝트는 8주 중 4주차를 지나고 있습니다. 데이터셋 빌드부터 학습, 평가, 품질 게이트, MLflow 등록, onnxruntime 추론 서버까지의 파이프라인은 코드와 테스트로 연결했습니다. 아직 MVP 데모 전이므로, 사용자가 앱에서 사진을 찍고 후보를 고치는 흐름 전체를 시연하지는 않았습니다.

아직 확인하지 못한 것도 많습니다.

- 사용자의 수정 데이터로 재학습하는 고리는 아직 한 번도 돌지 않았습니다. 지금 학습 데이터는 공개 데이터셋뿐이며, 승인된 수정 데이터를 읽는 빌드는 구현하지 않았습니다.
- 실사용 사진 평가는 26장 규모입니다. 실사용 조건의 정확도를 판단하기에는 표본이 작습니다.
- 크롭 기준과 전체 사진 기준의 큰 차이를 줄이는 방법(음식 영역 검출 후 분류 등)은 시도하지 않았습니다.
- AI 협업 규칙의 효과, 예를 들어 독립 리뷰가 병합 후 결함을 얼마나 줄였는지는 아직 측정하지 않았습니다. 엄격 MR 5건이 연속으로 병합 후 누락 0건이면 리뷰를 완화하고, 표준 MR에서 누락이 나오면 트리거를 넓히는 기준만 정해 두었습니다.

꾸기에서 제가 맡은 일은 모델의 정확도를 올리는 데서 끝나지 않았습니다. 그 숫자가 어떤 조건에서 나왔는지 밝히고, 다음 모델과 같은 조건에서 비교할 수 있게 만드는 일이었습니다. 6명이 AI 도구와 함께 일하는 방식도 같은 생각으로 정했습니다. 빠르게 만드는 것보다, 무엇을 확인했고 무엇을 확인하지 않았는지 남기는 것을 기준으로 삼았습니다.
