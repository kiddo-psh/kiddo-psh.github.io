## 문제

선착순 쿠폰 발급 기능이었다. 재고 1,000장을 정해두고 이벤트 시작과 동시에 신청을 받는다. 요구사항은 두 줄로 요약된다 — **재고보다 많이 발급되면 안 되고, 한 사람이 두 장 받으면 안 된다.**

첫 배포 후 이벤트에서 두 조건이 모두 깨졌다. 1,000장 재고에 1,014장이 발급되고, 중복 발급이 37건 나왔다.

원인은 조회와 갱신 사이의 틈이었다. 코드는 이렇게 생겼다.

```java
if (couponRepository.countByEvent(eventId) >= event.getStock()) {
    throw new SoldOutException();
}
if (couponRepository.existsByUserAndEvent(userId, eventId)) {
    throw new DuplicateException();
}
couponRepository.save(new Coupon(userId, eventId));
```

읽은 시점의 재고와 저장하는 시점의 재고가 다르다. 요청이 순차적으로 오면 문제가 없고, 동시에 오면 여러 요청이 같은 값을 읽는다. 부하 테스트로 재현해보니 동시 사용자 500명에서 100% 재현됐다.

## 아키텍처

세 가지 방법을 검토했다.

| 방법 | 정확성 | 처리량 | 문제 |
|---|---|---|---|
| 비관적 락 (`SELECT ... FOR UPDATE`) | 보장됨 | 낮음 | 재고 행 하나에 모든 요청이 직렬화됨 |
| 낙관적 락 (`@Version`) | 보장됨 | 중간 | 경합이 심하면 재시도가 폭증 |
| Redis 원자적 연산 | 보장됨 | 높음 | 영속화가 비동기라 정합성 관리 필요 |

선착순 이벤트는 **경합이 극단적으로 심한 대신 짧게 끝나는** 성격이다. 낙관적 락은 이 조건에서 재시도가 재시도를 부른다. 비관적 락은 정확하지만 재고 행 하나가 전체 처리량의 상한이 된다.

Redis를 택했다. 재고 차감과 중복 검사를 하나의 원자적 연산으로 묶고, 실제 쿠폰 레코드 저장은 큐를 통해 비동기로 넘겼다.

```
요청 → Redis Lua 스크립트 (재고 차감 + 중복 검사, 원자적)
        │
        ├─ 실패 → 즉시 응답 (품절 / 중복)
        └─ 성공 → 큐에 발급 이벤트 → 워커가 MySQL에 저장
```

핵심은 Lua 스크립트다. Redis는 스크립트 실행 중에 다른 명령을 끼워넣지 않으므로, 두 연산 사이에 틈이 생기지 않는다.

```lua
-- KEYS[1]: 재고 카운터, KEYS[2]: 발급자 Set
-- ARGV[1]: userId
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
  return -1  -- 이미 발급받음
end
local left = tonumber(redis.call('GET', KEYS[1]) or '0')
if left <= 0 then
  return -2  -- 품절
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return left - 1
```

## 내 역할

백엔드 3명 중 발급 API와 동시성 제어 설계를 담당했다. 구체적으로 한 일은 세 가지다.

**동시성 방식 선정과 근거 문서화.** 위의 세 가지 비교표를 만들고 팀에 제안했다. Redis를 택하면서 감수하는 것(장애 시 재고 정보 유실 가능성)과 그에 대한 대비(주기적 스냅샷, 이벤트 종료 후 정합성 검증 배치)를 함께 정리했다.

**Lua 스크립트 작성과 경계 조건 검증.** 재고가 정확히 0이 되는 순간, 같은 사용자가 동시에 두 번 요청하는 경우, 스크립트 실행 중 Redis가 죽는 경우를 각각 테스트로 만들었다.

**부하 테스트 설계.** 동시 사용자 500명으로 시작해 1,000명까지 올리며 재고 초과와 중복 발급을 세는 스크립트를 작성했다. 여기서 초기 구현의 문제를 한 번 더 발견했는데, 큐 소비 속도가 생산 속도를 못 따라가 이벤트 종료 후 30초까지 저장이 밀렸다. 워커를 3개로 늘려 해결했다.

## 결과

동시 요청 1만 건 기준으로 재고 초과 0건, 중복 발급 0건이 됐다.

응답시간이 줄어든 것은 부수 효과다. 기존 구현은 DB를 세 번 왕복했고(카운트, 중복 검사, 저장), 바꾼 구현은 Redis 왕복 한 번으로 응답한다. p99가 1,240ms에서 180ms가 된 대부분이 여기서 나왔다.

남은 과제가 두 개 있다.

**재고 복원이 수동이다.** 발급 후 사용자가 취소하면 Redis 카운터를 되돌려야 하는데, 지금은 운영자가 직접 스크립트를 돌린다. 취소가 드물어서 미뤘지만, 자동화하지 않으면 언젠가 실수가 난다.

**Redis 장애 시나리오가 검증되지 않았다.** 스냅샷과 검증 배치는 만들어뒀지만, 실제로 Redis를 죽이고 복구하는 훈련은 못 해봤다. 이벤트 중에 죽으면 어떤 상태로 남는지 아직 모른다.
