영화 추천이 준비돼 있어도 사용자가 가입하지 못하거나, 비밀번호를 바꾼 뒤 예전 재설정 링크가 계속 유효하다면 서비스를 안심하고 쓰기 어렵습니다. 화면에 보이는 추천 수치가 서버에서 제공하지 않는 값이어도 문제가 됩니다.

feelm에서 저는 계정·인증 백엔드와 화면의 API 연동을 맡았습니다. 이 글에서는 정상 로그인 뒤에 가려지기 쉬운 실패 조건과, 목업 화면을 실제 데이터에 맞추는 과정에서 내린 선택을 정리합니다.

## 영화 추천을 쓰기까지의 가입·인증·화면 연결을 맡았다

feelm은 감상한 영화를 필름 한 칸으로 기록하고, 영화 취향을 팝콘 맛으로 보여주는 서비스입니다. 팀은 MovieLens 32M과 영화 메타데이터를 처리해 취향 맞춤·취향 발견·파티 추천을 구성했습니다.

저는 가입·로그인·재설정·소셜 인증·탈퇴·차단을 구현했습니다. 정상 요청뿐 아니라 반복 발송, 만료된 인증 수단, 상태가 바뀐 계정의 요청도 다뤄야 했습니다. 이후에는 공통 HTTP 클라이언트와 인증 세션, 주요 화면을 실제 API에 연결했습니다.

## 인증 메일을 반복해서 보내는 요청은 어떻게 막을까?

같은 이메일 주소로 연속 발송하는 요청만 막으면, 주소를 바꿔 요청하는 경우를 다룰 수 없습니다. 한 가지 제한으로 묶는 대신 이메일·IP·전체 발송량으로 나눴습니다.

| 제한 기준 | 다루려는 요청 |
| --- | --- |
| 이메일 주소 | 같은 주소로 반복 발송 |
| 접속 IP | 주소를 바꾸며 반복 발송 |
| 전체 발송량 | 여러 요청으로 서비스의 발송 한도를 소진 |

제한 응답 자체가 계정 존재 여부를 드러내지 않는지도 계약 테스트로 확인했습니다. IP는 요청에 적힌 값을 무조건 믿지 않고, 신뢰하도록 정한 프록시의 클라이언트 IP만 채택했습니다.

이 구현과 테스트는 어떤 요청을 제한할지 명시한 근거입니다. 실제 공격 트래픽의 차단율이나 사용자 불편을 측정한 결과는 없으므로, 운영에서의 효과와 제한값의 적절성은 별도로 확인해야 합니다.

## 비밀번호를 바꿨는데 예전 재설정 링크가 살아 있다면?

비밀번호 재설정 메일을 받은 뒤 로그인 상태에서 비밀번호를 변경해도, 먼저 받은 링크는 만료 전까지 유효할 수 있었습니다. 비밀번호를 바꾸는 기능 하나만 보면 정상 동작하지만, 다른 경로에서 발급한 인증 수단과 함께 보면 상태가 어긋납니다.

비밀번호가 바뀌는 모든 경로에서 해당 계정의 재설정 토큰을 무효화하도록 정리했습니다. 기준을 개별 API가 아니라 **비밀번호가 변경됐다는 계정 상태 변화**에 뒀습니다.

## 탈퇴와 비밀번호 재설정이 동시에 들어오면 어떻게 될까?

탈퇴와 재설정이 토큰·계정의 잠금을 서로 다른 순서로 잡으면, 상대가 잡은 잠금이 풀리기를 기다리는 교착이 생길 수 있었습니다.

계정 익명화를 먼저 확정하고, 이후 토큰과 세션 등을 정리하는 구조로 나눴습니다. 탈퇴 서비스는 계정 변경 뒤 아바타 삭제, refresh token 폐기, 인증 토큰·차단 관계·파티 정리를 이어갑니다.

잠금과 정리 범위를 나누면 중간 실패도 다뤄야 합니다. 계정 상태 변경은 끝났는데 후속 정리가 실패할 수 있기 때문입니다. 동시성 테스트로 경쟁 요청의 회귀를 확인했지만, 모든 외부 정리의 재시도와 복구까지 입증한 것은 아닙니다.

데이터를 바꾸는 작업에도 같은 관점을 적용했습니다. 가입 인증 방식의 마이그레이션에서는 예상 밖 연관 데이터가 있으면 삭제 전에 실패하도록 가드를 뒀습니다. 연관 삭제 기능이 있다는 이유로 예상하지 못한 데이터까지 지워지지 않도록 확인하는 장치였습니다.

## 서버가 주지 않는 ‘취향 일치도’를 화면에 표시해도 될까?

화면을 실제 API에 연결하자 목업이 기대한 정보와 서버가 보장하는 정보가 다른 곳이 드러났습니다. OTT 추천 화면에는 취향 일치도 %, 추천 이유, 항목별 일치도가 있었지만 API-068이 제공하는 값은 시청 가능한 영화 수와 대표 영화 등이었습니다.

추천 점수는 상대적인 순위를 위한 값이었고, 유사도나 확률로 표시하지 않기로 정해져 있었습니다. 이 값을 그대로 백분율로 바꾸면 사용자가 수치의 의미를 잘못 이해할 수 있습니다.

화면의 일치도와 이유를 제거하고, 서버가 설명할 수 있는 `matchCount`와 `topMovies`를 사용하도록 API·요구사항·화면 문서를 함께 정리했습니다. 단건 조회는 새 API를 추가하지 않고 목록에서 찾는 방식을 유지했습니다.

## 운영에서 확인해야 할 실패와 복구가 남아 있다

사용자 이탈률이나 인증 장애율의 전후 비교는 확보하지 못했습니다. 테스트가 통과했다는 사실을 실제 사용자의 실패가 줄었다는 결과로 바꿔 설명할 수는 없습니다.

다음에는 가입·재설정·탈퇴의 실패를 단계별로 관측하고, 후속 정리가 실패했을 때 재시도와 복구가 가능한지 확인하려 합니다. 계정 상태 변화가 서버 응답에서 끝나지 않고 화면과 관련 인증 수단에 일관되게 반영되는지도 함께 점검해야 합니다.
