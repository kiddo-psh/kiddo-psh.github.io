## 추천 결과에 도달하기 전의 사용 흐름을 맡았다

feelm은 감상한 영화를 필름 한 칸으로 기록하고 취향을 팝콘 맛으로 보여줍니다. 팀은 MovieLens 32M과 영화 메타데이터를 처리해 취향 맞춤·취향 발견·파티 추천을 구성했습니다.

![취향 필름과 팝콘을 보여주는 실제 화면](/images/projects/feelm/02-pc-film.webp)

저는 계정·인증을 맡았습니다. 사용자가 가입하고 로그인하는 정상 경로와 함께 공격 시도, 만료된 인증 수단, 상태가 바뀐 계정의 요청을 신경 썼습니다. 이후에는 목업 화면을 실제 API에 연결하며 화면과 서버의 계약을 맞추는 일까지 맡았습니다.

## 결정 1. 메일 발송을 세 가지 축으로 제한하기

같은 이메일로 연속 요청하는 것만 막아서는 주소를 바꾸는 발송을 제한할 수 없습니다. 제한을 이메일·IP·전역 발송량으로 나눴습니다. 각 축이 막는 행위가 다르기 때문입니다.

| 제한 축 | 다루려는 요청 |
| --- | --- |
| 이메일 | 같은 주소로 반복 발송 |
| IP | 주소를 바꾸어 반복 발송 |
| 전역 | 여러 요청으로 전체 발송 쿼터 소진 |

제한 응답이 계정 존재 여부를 드러내지 않는지 계약 테스트로 확인하고 신뢰할 프록시의 클라이언트 IP만 채택하도록 처리했습니다. 실제 공격 트래픽의 차단율을 측정한 결과는 없지만, 어떤 요청을 같은 행위로 묶을지는 코드와 테스트로 명시했습니다.

## 결정 2. 비밀번호 변경의 효과를 모든 경로에 적용하기

재설정 메일을 받은 뒤 로그인 상태에서 비밀번호를 바꾸더라도 기존 재설정 링크가 만료 전까지 살아 있을 수 있었습니다. 비밀번호가 바뀌는 모든 경로에서 해당 계정의 재설정 토큰을 무효화하도록 정리했습니다.

![비밀번호 변경 시 재설정 토큰을 무효화하는 흐름](/images/projects/feelm/01-reset-token.svg)

중요한 단위는 개별 엔드포인트보다 비밀번호가 바뀌었다는 상태 변화였습니다. 어떤 경로로 바뀌든 기존 인증 수단에 같은 효과가 적용되어야 했습니다. 이 변경은 b19d1089에 남아 있습니다.

## 결정 3. 탈퇴의 잠금과 후속 정리 범위를 나누기

탈퇴와 비밀번호 재설정이 토큰·계정 잠금을 다른 순서로 잡으면 교착이 생길 수 있었습니다. 계정 익명화를 먼저 확정하고 토큰·세션 등의 정리를 이어가는 구조로 나눴습니다.

탈퇴 서비스는 계정 변경 뒤 아바타 삭제, refresh token 폐기, 인증 토큰·차단 관계·파티 정리를 호출합니다. 여러 단계로 나눈 만큼 중간 실패와 복구도 고려해야 합니다. 동시성 테스트는 요청 경쟁의 회귀를 확인하지만 모든 외부 정리의 복구까지 증명하지는 않습니다.

가입 인증 방식을 바꾸는 마이그레이션에서도 삭제 전에 예상 밖 연관 데이터가 있는지 확인하고 발견하면 실패하는 가드를 뒀습니다. CASCADE가 있는 데이터에서는 예상하지 못한 삭제를 사전에 멈추는 것이 필요했습니다.

## 화면 연동: 제공할 수 없는 일치도를 걷어내기

실제 API를 연결하면 목업 화면이 기대한 정보와 서버가 보장하는 정보가 다른 곳이 드러났습니다. OTT 추천 화면이 그 사례입니다.

화면에는 취향 일치도 %, 추천 이유, 항목별 일치도가 있었지만 API-068은 시청 가능한 영화 수인 matchCount와 대표 영화 등을 제공했습니다. 추천 점수는 상대 순위만 보장해 유사도나 확률로 표시하지 않기로 이미 정해져 있었습니다.

선택은 화면이 요구하는 수치를 임의로 채우는 대신 **서버가 설명할 수 있는 값으로 화면을 맞추는 것**이었습니다. d80dfb05에서 API·요구사항·화면 문서를 함께 정리해 일치도와 이유를 제거하고 matchCount와 topMovies를 사용하게 했습니다. 단건 조회는 새 API를 만들지 않고 목록에서 찾는 방식을 유지했습니다. 64532cd0에서 실제 연동이 이어졌습니다.

![평가에서 취향 기록으로 이어지는 화면](/images/projects/feelm/03-record-flow.webp)

이 과정은 변경 기록으로 확인한 사례입니다. 당시 팀 대화의 순서나 발언자는 기억으로 재구성하지 않았습니다. 남아 있는 결과는 화면·계약·응답이 같은 의미를 갖도록 정리한 변경입니다.

![추천·영화 상세·취향 리포트 화면](/images/projects/feelm/04-recommend.webp)

## 결과와 다음 검증

팀은 SSAFY 2학기 특화 프로젝트 1등을 기록했습니다. 제 기여는 인증의 실패 조건을 구현과 테스트로 남긴 일, 계정 상태 변화의 효과를 정리한 일, 화면을 실제 데이터와 연결한 일입니다. 주요 구현 기술은 Spring Boot·PostgreSQL·Redis·React이며 추천 데이터 처리와 모델은 팀 시스템의 구성입니다.

사용자 이탈률이나 인증 장애율의 전후 비교는 확보하지 못했습니다. 다음에는 가입·재설정·탈퇴의 실패를 단계별로 관측하고 후속 정리 실패의 재시도와 복구를 확인하려 합니다. 정상 응답을 만드는 것에서 실제 화면의 상태 전환까지 책임 범위를 넓힌 경험이었습니다.
