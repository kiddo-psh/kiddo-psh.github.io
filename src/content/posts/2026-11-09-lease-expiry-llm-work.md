[앞 글](/posts/redis-incr-race)에서는 Redis에서 자리 확인과 확보를 원자적으로 묶어야 한다는 점을 봤습니다. 그런데 작업자가 자리를 확보한 뒤 사라지면 누가 그 자리를 돌려줄까요? 이때 생각할 수 있는 방식이 **만료시각이 있는 사용 권한**, 즉 lease입니다.

가장 헷갈렸던 질문은 이것이었어요. **lease가 만료되면 이미 시작한 외부 LLM 호출도 끝날까?** 답은 아닙니다. lease는 공유 시스템이 인정하는 점유권의 수명이고, 외부 호출의 실행 상태와는 별개예요.

## lease를 한 자리의 이용권으로 생각하기

동시 호출 한 자리를 차지할 때 다음 정보를 기록한다고 가정하겠습니다.

```text
자리: llm-slot-2
소유권 토큰: A-7f3...
만료 시각: 12:00:30
```

작업자 A가 살아 있으면 만료 전에 이용권을 갱신합니다. 정상 종료하면 **자신의 토큰이 아직 그 자리의 소유자인지 확인한 뒤** 해제합니다. 강제 종료로 정리 코드가 실행되지 않아도 갱신이 멈추므로, TTL이 지나면 다른 작업이 자리를 회수할 수 있어요.

여기서 `try/finally`는 정상적인 예외 처리와 취소에 유용하지만, 프로세스가 강제 종료될 때까지 실행을 보장하지 않습니다. 따라서 장애 뒤 회복을 `finally`에만 맡기면 안 됩니다.

## A가 늦게 돌아오면 왜 토큰을 확인해야 할까

다음 순서를 보겠습니다.

| 시각 | 일어난 일 |
| --- | --- |
| 12:00:00 | A가 토큰 `A`로 자리를 확보하고 외부 LLM을 호출 |
| 12:00:30 | A의 lease가 만료. 갱신도 실패 |
| 12:00:31 | B가 같은 자리를 새 토큰 `B`로 확보 |
| 12:00:35 | A의 외부 호출이 뒤늦게 끝남 |

이때 A가 무조건 `DEL llm-slot-2`를 하면 B의 유효한 lease를 지워버립니다. 해제는 **저장된 토큰이 내 토큰과 일치할 때만** 해야 하고, 비교와 삭제도 하나의 원자적 작업이어야 해요. [Redis의 분산 잠금 문서](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)는 소유권을 확인하고 해제하는 Lua 패턴을 설명합니다.

```lua
-- KEYS[1]: lease 키, ARGV[1]: 내가 발급받은 토큰
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

이 코드는 **한 자리의 소유권 확인 후 해제**를 보여주는 최소 예시입니다. 여러 자리의 동시성 제한을 구현하려면 각 점유의 만료·갱신·회수를 함께 설계해야 합니다.

## 만료는 외부 작업을 취소하지 않는다

위 시간표에서 12:00:31부터 12:00:35까지 B는 유효한 자리를 차지하고 있지만, A의 외부 LLM 호출도 아직 끝나지 않았습니다. 따라서 lease 점유 수가 설정한 상한 이하여도 **실제로 실행 중인 외부 호출 수는 순간적으로 상한을 넘을 수 있어요.**

이 차이가 중요합니다. Redis에 기록된 lease는 “누가 지금 권한을 가진 것으로 보는가”에 답합니다. 외부 서비스에서 진행 중인 호출은 별도의 현실이에요. lease 만료만으로 강제 중단이나 절대적인 외부 동시 호출 상한을 보장한다고 쓰면 안 됩니다.

운영 설계에서는 다음을 함께 고려해야 합니다.

- 외부 호출 자체의 타임아웃과 전체 요청의 데드라인
- lease 갱신 실패 시 새 작업 시작을 막고, 늦게 끝난 결과를 어떻게 처리할지
- 갱신 주기, TTL, 네트워크 장애, 프로세스 중단을 반영한 여유
- 자리 확보 대기와 요청 취소, 재시도가 만들 추가 부하

외부 호출을 취소할 수 있더라도 취소 요청이 이미 시작한 원격 작업을 즉시 중지한다는 보장은 별도로 확인해야 합니다. 늦게 끝난 작업이 저장소 같은 **내가 통제하는 자원**에 결과를 쓰는 문제라면, 더 새 소유자의 작업만 반영되도록 버전 번호나 fencing token을 검토할 수 있어요. 반면 외부 LLM 호출 그 자체의 중단을 fencing token이 대신하지는 않습니다.

## 작은 확인: 권한이 없어져도 코루틴은 돌아온다

아래 코드는 Redis 없는 **시간 흐름 모형**입니다. 실제 분산 세마포어나 LLM 호출을 구현한 코드는 아니에요.

```python
import asyncio

async def old_call() -> None:
    await asyncio.sleep(0.06)  # 외부 호출이 오래 걸리는 상황을 흉내 낸다
    print("A의 호출 완료")

async def main() -> None:
    task_a = asyncio.create_task(old_call())
    await asyncio.sleep(0.03)
    print("A의 lease 만료, B가 자리 확보")
    await task_a  # lease 상태를 바꿔도 A의 태스크는 계속 진행한다

asyncio.run(main())
```

이 실험에서 출력되는 건 두 문장 모두입니다. lease 상태를 기록한 곳에서 A의 권한을 없앴다고 해서 `task_a`가 자동으로 취소되지는 않아요. 실제 서비스에서는 갱신·해제·중단 경로와 늦게 끝난 결과의 처리를 따로 정해야 합니다.

이 시리즈는 학습용 설계입니다. 제 프로젝트에서 Redis 분산 세마포어나 lease를 운영했다는 뜻이 아닙니다. 여기까지 나누어 보니 비동기 실행, 동시 실행 수 제한, 만료되는 권한이 각자 다른 질문에 답한다는 점이 분명해졌습니다.
