주문 목록 API의 p99 응답시간이 어느 날부터 1.2초를 넘겼다. 데이터가 갑자기 늘어난 것도 아니고, 코드를 배포한 것도 아니었다. 원인을 찾는 데 이틀이 걸렸고, 그 사이에 나는 원인을 세 번 잘못 짚었다. 이 글은 그 세 번의 오진과, 결국 무엇을 봐야 했는지에 대한 기록이다.

> **결론부터**: 요청 한 번에 쿼리가 201개 나가고 있었다. 애플리케이션 코드는 한 줄도 바뀌지 않았고, 바뀐 것은 한 주문에 딸린 상품의 개수였다.

## 문제 상황

주문 목록은 관리자 화면의 첫 페이지다. 한 번에 20건씩 보여주고, 각 주문에는 주문 상품과 배송 정보가 함께 표시된다. 특별할 것 없는 화면이고, 6개월 동안 200ms 안쪽에서 응답했다.

그런데 모니터링 대시보드의 그래프가 어느 날부터 계단식으로 올라갔다.

| 구간 | p50 | p99 | 처리량 |
|---|---|---|---|
| 정상 시기 | 90ms | 210ms | 340 rpm |
| 문제 발생 후 | 470ms | 1,240ms | 310 rpm |

처리량은 그대로였다. 트래픽이 늘어서 느려진 게 아니라는 뜻이다. 이 지점에서 이미 단서가 있었는데 나는 다른 곳을 봤다.

## 세 번의 오진

### 오진 1: 인덱스가 없을 것이다

가장 먼저 의심한 건 인덱스였다. 느린 쿼리 로그를 켜고 `slow_query_log`에 잡힌 쿼리를 봤다. 그런데 개별 쿼리는 하나도 느리지 않았다. 전부 1ms 안쪽이었다.

여기서 멈추고 생각을 바꿨어야 했다. **개별 쿼리가 모두 빠른데 전체가 느리다는 것은, 쿼리 하나가 무거운 게 아니라 쿼리가 너무 많다는 뜻이다.** 하지만 그때는 "느린 쿼리 로그에 안 잡혔으니 DB 문제는 아니다"라고 결론을 내려버렸다.

### 오진 2: 커넥션 풀이 부족할 것이다

DB가 아니라면 커넥션을 기다리는 것이라고 생각했다. HikariCP 풀 크기를 10에서 30으로 올렸다.

응답시간이 1,240ms에서 1,180ms로 줄었다. 5% 개선. 이건 개선이 아니라 잡음이다. 그런데 나는 "방향은 맞는데 부족하다"고 해석했다. 이게 두 번째 오진이고, 첫 번째보다 나쁘다. **숫자가 거의 안 움직였는데 방향이 맞다고 믿은 것이기 때문이다.**

### 오진 3: 직렬화가 무거울 것이다

응답 JSON이 크니 직렬화 비용일 것이라고 봤다. 응답 필드를 절반으로 줄여봤다. 1,180ms에서 1,150ms. 또 잡음이었다.

세 번째 오진까지 오는 데 하루 반이 걸렸다. 공통점이 있다. **세 번 모두 "무엇이 느린지"를 측정하지 않고 "무엇이 느릴 것 같은지"를 고쳤다.**

## 쿼리 로그를 켜다

결국 애플리케이션이 실제로 어떤 쿼리를 몇 번 보내는지 보기로 했다. 개발 환경에서 SQL 로그를 전부 출력하게 했다.

```properties
# application-local.properties
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
logging.level.org.hibernate.orm.jdbc.bind=trace
```

요청 한 번을 보내고 로그 줄 수를 셌다.

```bash
$ grep -c "select" app.log
201
```

201개. 주문 20건을 가져오는 쿼리 1개, 그리고 각 주문마다 상품을 가져오는 쿼리 20개, 각 상품마다 옵션을 가져오는 쿼리 180개. 전형적인 N+1이고, 그것도 두 단계로 중첩된 형태였다.

문제의 코드는 이렇게 생겼다.

```java
List<Order> orders = orderRepository.findAll(pageable).getContent();

return orders.stream()
    .map(order -> new OrderResponse(
        order.getId(),
        order.getItems().stream()          // ← 주문마다 쿼리 1번
            .map(item -> new ItemResponse(
                item.getName(),
                item.getOptions()          // ← 상품마다 쿼리 1번
            ))
            .toList()
    ))
    .toList();
```

`getItems()`와 `getOptions()`는 기본이 지연 로딩이다. 스트림 안에서 이걸 건드리는 순간 쿼리가 나간다. 코드만 보면 반복문이 세 겹이라는 게 잘 안 보이는데, 그게 이 버그가 6개월을 살아남은 이유다.

## 왜 갑자기 느려졌는가

여기서 처음 질문으로 돌아간다. 코드가 안 바뀌었는데 왜 느려졌나.

N+1의 N은 데이터 개수다. 서비스 초기에는 한 주문에 상품이 1~2개였다. 그때 쿼리는 20 + 30 = 약 50개였고, 개당 1ms면 50ms다. 눈에 안 띈다.

그런데 상품 묶음 판매를 도입하면서 한 주문의 평균 상품 수가 9개로 늘었다. 쿼리는 20 + 180 = 200개가 되고, 200ms가 된다. 여기에 네트워크 왕복과 영속성 컨텍스트 오버헤드가 붙어 1.2초가 됐다.

> **이 버그의 성질**: N+1은 배포 시점에 터지지 않는다. 데이터가 자라면서 서서히 터진다. 그래서 "최근 배포한 것"을 의심하는 습관으로는 찾을 수 없다.

## 해결

두 단계 연관을 한 번에 가져오도록 바꿨다.

```java
@Query("""
    select distinct o from Order o
    join fetch o.items i
    join fetch i.options
    where o.status = :status
    """)
List<Order> findAllWithItemsAndOptions(@Param("status") OrderStatus status);
```

결과는 이렇게 바뀌었다.

| 지표 | 이전 | 이후 |
|---|---|---|
| 요청당 쿼리 수 | 201개 | 1개 |
| p50 | 470ms | 62ms |
| p99 | 1,240ms | 180ms |

응답시간이 7분의 1이 됐다. 커넥션 풀도 원래 크기로 되돌렸다 — 그건 애초에 문제가 아니었다.

### 대안으로 검토한 것들

`fetch join` 말고도 선택지가 있었다.

- **`@BatchSize`** — 쿼리를 `IN` 절로 묶어 201개를 3개로 줄인다. 페이징과 함께 써도 안전하다는 게 장점이다.
- **`@EntityGraph`** — 같은 효과를 어노테이션으로 선언한다. JPQL을 안 써도 된다.
- **DTO 직접 조회** — 필요한 컬럼만 `select new`로 가져온다. 가장 빠르지만 엔티티를 못 쓴다.

이번에는 조건이 단순하고 페이징을 서비스 계층에서 처리할 수 있어서 `fetch join`을 택했다. 목록에 페이징이 필수였다면 `@BatchSize`로 갔을 것이다. 이유는 아래에 적었다.

## 남은 것

`fetch join`과 페이징을 함께 쓰면 하이버네이트가 경고를 남긴다.

```
HHH90003004: firstResult/maxResults specified with collection fetch;
applying in memory
```

컬렉션을 조인하면 결과 행이 부풀기 때문에, DB에서 `LIMIT`으로 자를 수가 없다. 그래서 하이버네이트는 **전체를 메모리로 가져온 뒤 자른다.** 주문이 100만 건이면 100만 건을 다 읽는다.

이번에는 조건절이 특정 상태의 주문만 걸러서 결과가 수백 건이라 문제가 되지 않았다. 하지만 이건 조건이 바뀌면 언제든 터질 수 있는 구조다. 다음에 이 API에 페이징이 붙는다면 `@BatchSize`로 옮겨야 한다.

정리하면 이번에 배운 것은 두 가지다.

1. **개별 쿼리가 모두 빠른데 전체가 느리면, 쿼리 개수를 세라.** 느린 쿼리 로그는 이 경우를 잡지 못한다.
2. **숫자가 5% 움직였을 때 "방향은 맞다"고 해석하지 마라.** 그건 아무것도 안 고쳤다는 뜻이다.
