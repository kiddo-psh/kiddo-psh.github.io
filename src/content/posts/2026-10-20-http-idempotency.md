[앞 글](/posts/http-request-response)에서는 타임아웃만으로 서버 작업이 실패했다고 단정할 수 없다는 점을 정리했어요. 서버는 작업을 완료했지만 성공 응답만 유실됐을 수 있기 때문입니다. 이 상태에서 같은 요청을 다시 보내면 작업이 두 번 생성될 수 있어요.

냠냠코치에서 식단 분석 작업을 등록하는 가상의 API를 예로 들어, 재시도를 안전하게 처리하려면 무엇이 필요한지 살펴보겠습니다.

## 멱등성의 기준은 응답이 아니라 효과다

멱등성은 동일한 요청을 여러 번 실행해도 **의도한 서버 측 효과가 한 번 실행했을 때와 같은 성질**입니다.

에어컨에 “온도를 24도로 설정해”라는 명령을 반복하면 설정 온도는 24도로 유지됩니다. 반면 “온도를 1도 내려”라는 명령은 보낼 때마다 온도가 내려가요. 첫 번째 명령이 멱등한 동작의 예시입니다.

HTTP에서는 PUT, DELETE와 GET 같은 안전한 메서드를 멱등한 것으로 정의합니다. 여기서 응답까지 같아야 하는 것은 아니에요. `DELETE /documents/42`가 처음에는 `204`, 다음에는 `404`를 반환하더라도 문서가 없는 상태라는 효과는 같습니다. 요청마다 접근 로그가 쌓이는 것도 이 정의와 모순되지 않습니다.

## 같은 작업의 재시도에는 같은 키를 쓴다

POST는 메서드 자체로 멱등성을 보장하지 않습니다. 작업 생성 요청에서 중복을 막으려면 서버와 클라이언트가 별도의 처리 규칙을 정할 수 있어요. 그 방법 중 하나가 멱등성 키입니다.

```http
POST /meal-analysis
Idempotency-Key: abc-123
Content-Type: application/json

{"mealId": 42}
```

이 API가 해당 헤더를 지원한다고 가정하면, 클라이언트는 논리적인 작업을 시작할 때 키를 만들고 재시도에도 그대로 사용합니다. 재시도마다 새 키를 만들면 서버가 각각을 새로운 작업으로 판단할 수 있어요.

반대로 사용자가 새로운 분석을 의도했다면 새 키를 사용해야 합니다. 같은 식단이라도 다시 분석하고 싶을 수 있으므로 식단 ID만으로 모든 요청을 중복 처리하면 안 돼요. **입력이 같다는 것과 작업 의도가 같다는 것은 다릅니다.**

## 고객 ID와 유일성 제약은 각각 무슨 역할일까?

고객별로 키를 관리하는 설계에서는 다음 세 가지를 구분해야 합니다.

| 구분 | 역할 |
| --- | --- |
| 고객 ID | 누가 요청했는지 식별 |
| 멱등성 키 | 어떤 논리적 작업인지 식별 |
| DB 유일성 제약 | 같은 조합의 중복 저장을 방지 |

`(user-17, abc-123)`과 `(user-28, abc-123)`은 다른 사용자의 작업입니다. 이 설계에서는 같은 고객이 같은 키를 보내야 같은 작업으로 판단해요. 고객 ID는 요청 본문을 그대로 믿기보다 서버가 로그인 토큰이나 세션 같은 인증 정보에서 확인합니다. 기존 결과를 반환할 때도 해당 고객의 접근 권한을 확인해야 하고요.

DB에는 다음과 같은 제약을 둘 수 있습니다.

```sql
UNIQUE (user_id, idempotency_key)
```

코드에서 기존 키를 조회하는 것만으로는 충분하지 않습니다. 요청 A가 “기록 없음”을 확인한 직후 요청 B도 같은 결과를 읽으면, 둘 다 작업을 생성하려 할 수 있어요. 유일성 제약은 같은 조합의 두 번째 저장을 막습니다. 서버는 이 충돌을 처리하고 기존 작업의 상태나 결과를 반환하도록 구현해야 합니다.

고객 ID를 키와 반드시 조합해야만 하는 것은 아닙니다. 키를 서비스 전체에서 유일하게 관리하는 설계도 있어요. 중요한 것은 키의 적용 범위를 명확히 정하고 그 범위에 맞게 중복과 접근 권한을 처리하는 것입니다.

## 작업 생성과 키 기록은 함께 저장한다

작업은 생성됐는데 키 기록이 실패하면, 재시도에서 기존 작업을 알아보지 못할 수 있습니다. 반대로 키만 기록되고 작업이 생성되지 않아도 문제가 됩니다. DB 안에서 작업을 등록하는 예시라면 두 변경을 같은 트랜잭션으로 묶어 둘 다 저장되거나 둘 다 저장되지 않도록 해야 해요.

같은 키로 다른 요청 내용이 들어왔을 때의 오류 처리, 처리 중인 작업에 대한 응답, 키 보관 기간도 정해야 합니다. 보관 기간이 끝난 키는 오래된 재시도를 새 요청으로 판단하게 만들 수 있어요. 또 DB의 작업 등록을 보호했다고 해서 외부 분석 서비스 호출까지 자동으로 중복 방지되는 것은 아닙니다.

멱등성 키는 같은 작업을 알아보는 식별자입니다. 실제 보장은 **동시 요청 처리, 저장 방식, 보관 기간과 적용 범위**를 포함한 서버 구현으로 완성돼요. [다음 글](/posts/backoff-jitter)에서는 중복을 막은 뒤에도 필요한 재시도 횟수와 시간 조절을 살펴봅니다.
