앱에서 식단 분석 버튼을 누르면 식단 정보가 서버로 전달되고, 결과가 화면에 나타납니다. 이때 클라이언트와 서버가 요청과 응답을 주고받는 규약이 HTTP예요. API를 다루려면 요청에 무엇을 담는지, 응답으로 무엇을 알 수 있는지부터 구분해야 합니다.

이번 글에서는 냠냠코치의 식단 분석을 가상의 API 예시로 사용합니다. 실제 구현을 설명하는 것은 아니에요.

## HTTP 요청을 구성하는 요소

식단 분석 작업을 등록하는 요청을 HTTP/1.1 형식으로 표현하면 다음과 같습니다.

```http
POST /meal-analysis HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"mealId": 42}
```

`POST`는 요청 메서드, `/meal-analysis`는 요청 대상 경로입니다. 헤더에는 서버가 요청을 해석하는 데 필요한 정보를 담아요. 여기서 `Content-Type`은 본문이 JSON 형식임을 나타냅니다. 본문에는 분석할 식단의 ID를 넣었어요.

대표적인 메서드의 의미는 다음과 같습니다.

| 메서드 | 의미 |
| --- | --- |
| GET | 대상 자원의 표현을 조회 |
| POST | 대상 자원에 데이터 처리를 요청 |
| PUT | 대상 자원의 상태를 생성하거나 대체 |
| DELETE | 대상 자원을 제거 |

메서드는 서버에 전달하는 작업의 의미입니다. `DELETE`라는 이름만 붙였다고 삭제가 저절로 되는 것은 아니에요. 서버가 해당 의미에 맞게 처리하도록 구현해야 합니다.

## 요청 성공과 분석 완료의 차이

서버가 작업을 등록한 뒤 다음과 같이 응답했다고 가정해볼게요.

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"jobId": "job-101", "status": "queued"}
```

`201 Created`는 자원이 생성됐다는 뜻입니다. 이 예시에서는 **분석 작업 등록이 성공한 것**이에요. 본문의 `queued`는 대기 중이라는 뜻이므로, 분석 결과까지 완성됐다고 해석하면 안 됩니다.

상태 코드는 첫 번째 숫자로 큰 범주를 나타냅니다.

| 범주 | 의미 |
| --- | --- |
| 2xx | 성공 |
| 3xx | 요청을 완료하기 위해 추가 동작이 필요 |
| 4xx | 요청 측에 오류가 있는 것으로 판단 |
| 5xx | 서버가 요청을 처리하는 과정에서 오류 발생 |

구체적인 대응은 개별 코드와 API 계약을 함께 봐야 해요. 입력이 잘못돼 `400 Bad Request`가 왔다면 같은 요청을 반복해도 해결되지 않습니다. `503 Service Unavailable`처럼 일시적인 처리 불가를 나타내면 재시도를 고려할 수 있지만, 중복 실행 위험과 서버의 대기 안내도 확인해야 합니다.

## 무상태 프로토콜에서 로그인을 유지하려면?

HTTP는 무상태 프로토콜입니다. 각 요청은 이전 요청의 맥락 없이도 해석할 수 있어야 해요. 그렇다고 서버가 사용자 정보를 저장할 수 없다는 뜻은 아닙니다.

애플리케이션은 쿠키에 세션 식별자를 담거나 인증 토큰을 보내 사용자를 식별할 수 있습니다. 서버도 DB나 세션 저장소에 상태를 보관할 수 있어요. **HTTP 자체의 무상태성과 애플리케이션이 관리하는 상태는 구분해야 합니다.**

## 타임아웃이 발생하면 서버 작업도 실패한 걸까?

오류 응답을 받은 경우와 응답 자체를 받지 못한 경우도 다릅니다. 다음 순서를 생각해볼게요.

1. 클라이언트가 식단 분석 작업 등록을 요청합니다.
2. 서버가 작업을 생성하고 성공 응답을 보냅니다.
3. 네트워크 문제로 응답이 클라이언트에 도착하지 않습니다.
4. 클라이언트는 기다리다가 타임아웃을 겪습니다.

클라이언트가 확인한 사실은 **정해진 시간 안에 응답을 받지 못했다는 것**입니다. 서버에서 작업을 생성했는지는 아직 알 수 없어요.

이때 실패했다고 판단해 다시 요청하면 분석 작업이 두 번 생길 수 있습니다. 따라서 API를 설계할 때는 정상적인 요청과 응답뿐 아니라, 결과를 확인하지 못한 상황에서 어떻게 행동할지도 정해야 해요. [다음 글](/posts/http-idempotency)에서는 같은 작업의 재시도로 효과가 중복되지 않도록 하는 멱등성을 정리합니다.
