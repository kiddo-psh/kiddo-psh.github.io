인덱스를 추가했는데 쿼리가 그대로 느렸다. 인덱스가 있다는 사실과 인덱스를 쓴다는 사실은 다른 이야기인데, 그걸 실행 계획을 읽고 나서야 알았다.

## 인덱스를 탄다는 착각

문제가 된 쿼리는 이렇게 생겼다. 특정 날짜의 주문을 세는 통계용 쿼리다.

```sql
SELECT COUNT(*) FROM orders
WHERE DATE(created_at) = '2026-07-15';
```

`created_at`에는 인덱스가 있었다. 그런데 응답이 3초였다. 테이블은 400만 행이다.

`EXPLAIN`을 붙여봤다.

```sql
EXPLAIN SELECT COUNT(*) FROM orders
WHERE DATE(created_at) = '2026-07-15';
```

| id | select_type | table | type | key | rows | Extra |
|---|---|---|---|---|---|---|
| 1 | SIMPLE | orders | ALL | NULL | 3982104 | Using where |

`type`이 `ALL`이고 `key`가 `NULL`이다. 인덱스가 있는데 쓰지 않고 400만 행을 전부 읽었다.

## 왜 안 탔는가

이유는 `DATE(created_at)` 이다. 인덱스는 `created_at`의 **원래 값**으로 정렬되어 있다. 그런데 조건은 그 값에 함수를 씌운 결과를 비교한다. 옵티마이저 입장에서는 함수를 통과한 결과가 어떻게 정렬되는지 알 수 없으므로, 모든 행에 함수를 적용해보는 수밖에 없다.

> 인덱스가 걸린 컬럼을 조건절에서 **가공하면** 인덱스는 무력화된다. 함수, 연산, 타입 캐스팅 모두 해당한다.

같은 실수의 다른 형태들이다.

- `WHERE YEAR(created_at) = 2026`
- `WHERE price * 1.1 > 10000`
- `WHERE CAST(user_id AS CHAR) = '123'`
- `WHERE SUBSTRING(phone, 1, 3) = '010'`

전부 좌변을 건드렸다. 규칙은 하나다. **인덱스를 타게 하려면 컬럼을 그대로 두고 우변을 조정한다.**

## 고친 방법

함수를 걷어내고 범위 조건으로 바꿨다.

```sql
SELECT COUNT(*) FROM orders
WHERE created_at >= '2026-07-15 00:00:00'
  AND created_at <  '2026-07-16 00:00:00';
```

`EXPLAIN` 결과가 이렇게 바뀌었다.

| id | select_type | table | type | key | rows | Extra |
|---|---|---|---|---|---|---|
| 1 | SIMPLE | orders | range | idx_created_at | 8412 | Using where; Using index |

`type`이 `range`가 되고, `key`에 인덱스 이름이 잡혔다. 읽는 행이 398만에서 8천으로 줄었다. 응답은 3초에서 12ms가 됐다.

`Extra`의 `Using index`도 의미가 있다. 커버링 인덱스로 처리됐다는 뜻이다 — `COUNT(*)`에 필요한 정보가 인덱스 안에 다 있어서 테이블 데이터를 아예 읽지 않았다.

### 상한을 `<=` 대신 `<`로 쓴 이유

`BETWEEN '2026-07-15 00:00:00' AND '2026-07-15 23:59:59'`로 쓰는 경우를 자주 본다. 이건 미묘하게 틀렸다.

`created_at`이 소수점 초를 저장하면 `23:59:59.5`가 범위에서 빠진다. 하루에 몇 건씩 조용히 누락되는 통계가 만들어지고, 이건 아무 에러도 내지 않는다. **다음 구간의 시작점을 열린 상한으로 쓰는 게 항상 안전하다.**

## `EXPLAIN`에서 실제로 볼 것

이번에 정리한 읽는 순서는 이렇다.

1. **`type`** — 가장 중요하다. `ALL`이면 풀 스캔이다. `index`도 좋은 게 아니라 인덱스 전체를 훑는다는 뜻이다. `range`, `ref`, `eq_ref`, `const` 순으로 좋아진다.
2. **`key`** — `NULL`이면 인덱스를 쓰지 않았다. 여러 인덱스 중 예상과 다른 것을 골랐는지도 여기서 본다.
3. **`rows`** — 옵티마이저가 읽을 것으로 추정한 행 수다. 실제 결과 행 수와 자릿수가 다르면 헛일을 하고 있다는 신호다.
4. **`Extra`** — `Using filesort`와 `Using temporary`가 보이면 정렬이나 임시 테이블이 생겼다는 뜻이다. `Using index`는 반대로 좋은 신호다.

`rows`를 세 번째로 둔 이유가 있다. 이건 추정치이고 통계가 낡으면 실제와 크게 다르다. 정확한 값이 필요하면 `EXPLAIN ANALYZE`로 실제 실행 결과를 본다.

## 남은 것

복합 인덱스의 컬럼 순서를 정하는 기준은 아직 감으로 하고 있다. "선택도가 높은 컬럼을 앞에"라는 규칙은 알지만, 그 규칙이 정렬 조건이나 범위 조건과 만나면 어떻게 되는지는 매번 헷갈린다.

특히 `WHERE a = ? AND b > ? ORDER BY c` 같은 형태에서 `(a, b, c)`와 `(a, c, b)` 중 무엇이 나은지 설명할 수 없다. 다음에 이걸 실제 데이터로 재보고 정리할 생각이다.
