서버가 과부하로 요청을 처리하지 못할 때, 실패한 클라이언트들이 즉시 다시 요청하면 부하가 더 쌓일 수 있습니다. [앞 글](/posts/http-idempotency)의 멱등성으로 중복 작업을 막아도 이 문제는 남아요. 요청을 받고 인증하거나 기존 작업을 조회하는 데에도 자원이 필요하기 때문입니다.

재시도에는 중복 방지뿐 아니라 요청의 빈도와 시점을 조절하는 정책도 필요합니다. 이때 사용하는 도구가 백오프와 지터예요.

## 기다려도 동시에 기다리면 다시 몰린다

백오프는 재시도 전에 기다리는 방식입니다. 지수 백오프는 실패가 이어질수록 대기 시간을 지수적으로 늘려 반복 호출의 빈도를 낮춥니다.

하지만 클라이언트 1,000개가 동시에 실패하고 모두 1초를 기다리면 어떻게 될까요? 당장의 부하는 줄어도 1초 뒤에는 다시 함께 요청합니다. 지터는 대기 시간에 무작위성을 넣어 재시도 시점을 흩뜨려요.

Full Jitter 방식은 다음과 같이 대기 시간을 계산합니다.

```text
대기 상한 = min(최대 대기 시간, 기본 대기 시간 × 2ⁿ)
실제 대기 시간 = 0부터 대기 상한 사이의 무작위 값

n = 0부터 시작하는 재시도 순번
```

기본 대기 시간을 0.5초, 최대 대기 시간을 4초로 설정한 학습용 예시입니다.

| 재시도 순서 | 실제 대기 시간의 범위 |
| --- | --- |
| 첫 번째 | 0~0.5초 |
| 두 번째 | 0~1초 |
| 세 번째 | 0~2초 |
| 네 번째 이후 | 0~4초 |

무작위로 선택하므로 실제 대기 시간이 매번 길어지는 것은 아닙니다. 두 번째에 첫 번째보다 짧게 기다릴 수도 있어요. 최대 대기 시간에 도달하기 전까지 커지는 것은 대기 시간의 상한입니다.

## ‘5초 이내 재시도’ 요구사항은 어떻게 구현할까?

먼저 5초를 어디서부터 어디까지 측정할지 정해야 합니다. 실패를 확인한 시점부터인지, 최초 요청을 보낸 시점부터인지에 따라 구현이 달라져요.

| 요구사항 | 구현 방향 |
| --- | --- |
| 실패 확인 후 5초 이내에 다음 시도 시작 | 대기 상한을 5초 이하로 설정하고 실행 지연을 고려 |
| 최초 요청부터 5초 이내에 다음 시도 시작 | 최초 호출에 걸린 시간을 제외한 남은 시간 안에서 대기 |
| 재시도한 결과까지 총 5초 안에 반환 | 모든 호출과 대기를 포함한 전체 시간 제한 관리 |

최초 요청이 4초 후 타임아웃됐다면, 최초 요청부터 5초 이내에 다음 시도를 시작하기 위해 남은 시간은 약 1초입니다. 대기 상한을 단순히 5초로 설정하면 요구사항을 충족하지 못할 수 있어요.

전체 처리 시간이 5초로 제한된다면 최초 요청 시점에 마감 시각을 정합니다. 이후 각 실패 시점에 남은 시간을 계산하고, 그 안에서 대기와 다음 호출이 가능한지 판단해야 해요. 다음 호출의 타임아웃도 남은 시간에 맞춰야 합니다. 구현에서는 경과 시간 계산에 시스템 시각 변경의 영향을 받지 않는 단조 시계를 사용하는 편이 적절합니다.

대기 함수를 5초로 설정했다고 실제 네트워크 요청이 정확히 5초 안에 시작하거나 완료된다고 보장되지는 않습니다. 스케줄링과 통신 지연도 있기 때문에, 엄격한 시간 조건이라면 그 여유까지 포함해 정책을 정해야 해요.

서버가 `Retry-After: 5`로 대기 시간을 안내했는데 전체 시간이 3초밖에 남지 않았다면 두 조건을 함께 만족하는 재시도는 불가능합니다. 이때는 재시도를 중단하고 상태를 반환하거나, 서비스가 지원한다면 비동기 처리로 전환하는 정책이 필요합니다.

## 여러 계층의 재시도는 횟수를 곱할 수 있다

다음과 같은 호출 구조를 가정해볼게요.

```text
고객 앱 → 업무 서버 → AI 연동 서버 → 분석 서비스
```

세 호출 계층이 각각 최초 호출을 포함해 최대 3회씩 시도하면, 모든 시도가 실패하는 경우 분석 서비스에는 최대 `3 × 3 × 3 = 27회`의 호출이 발생할 수 있습니다. 재시도 횟수를 계층별로만 보면 놓치기 쉬운 부분이에요.

따라서 호출별로 재시도 담당을 정하고 정책을 조율해야 합니다. 예를 들어 분석 서비스의 일시적 오류는 AI 연동 서버가 재시도하고, 상위 계층은 전체 제한 시간을 관리하도록 설계할 수 있어요. AI 연동 서버 자체에 연결하지 못한 경우라면 업무 서버가 해당 호출의 재시도를 담당할 수도 있습니다. 어느 계층이 맡든 내부 재시도와 겹쳐 호출이 증폭되지 않도록 해야 합니다.

재시도 전에는 오류가 일시적인지, 중복 실행을 막을 수 있는지, 남은 횟수와 시간이 충분한지 확인합니다. 같은 작업이라면 멱등성 키도 유지해요. 최대 재시도가 3번이라면 최초 요청을 포함한 최대 호출 횟수는 4번이라는 점도 구분해야 합니다.

백오프와 지터는 재시도 시점을 조절하는 도구입니다. 실제 정책은 **재시도 가능한 오류, 담당 계층, 최대 시도 횟수, 전체 시간 예산**을 함께 정해야 완성됩니다.
