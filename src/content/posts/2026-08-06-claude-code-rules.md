에이전트에게 리팩터링을 맡기기 시작한 지 넉 달쯤 됐다. 처음 두 달은 손해였다. 결과물이 나쁜 게 아니라, **결과물이 맞는지 확인하는 비용이 직접 고치는 비용보다 컸다.** 지금은 이득이 나는데, 달라진 건 도구가 아니라 내가 정한 규칙이다.

세 가지다. 순서대로 중요하다.

## 규칙 1: 되돌릴 수 있는 상태에서만 맡긴다

가장 처음 정한 규칙이고, 나머지 두 개는 사실 이것의 파생이다.

에이전트에게 작업을 맡길 때 내가 실제로 하는 판단은 "이걸 잘할까"가 아니라 **"잘못했을 때 내가 알아챌 수 있나"** 다. 알아챌 수 있으면 맡기고, 못하면 맡기지 않는다.

### 알아챌 수 있는 상태의 조건

- 커밋되지 않은 변경이 없다. 그래야 `git diff`가 에이전트의 작업만 보여준다.
- 테스트가 있고, 지금 통과한다. 통과하는 걸 본 뒤에 맡겨야 실패가 새로 생긴 건지 알 수 있다.
- 작업 범위가 한 번에 읽을 수 있는 크기다. diff가 500줄을 넘으면 나는 사실상 안 읽는다.

세 번째가 제일 자주 깨진다. "이 모듈 전체를 정리해줘"는 되돌릴 수 없는 요청이다. 결과가 800줄 diff로 오고, 나는 그걸 다 읽지 않고 테스트가 초록이면 넘긴다. 그건 리뷰가 아니라 도박이다.

> **Try:** "이 파일에서 중복된 검증 로직만 추출해줘. 다른 건 건드리지 말고, 끝나면 무엇을 바꿨는지 3줄로 요약해줘."
>
> 범위를 파일 하나와 관심사 하나로 묶으면 diff가 읽을 수 있는 크기로 나온다.

### 테스트가 없는 코드는 어떻게 하나

테스트가 없으면 두 단계로 나눈다. 먼저 **테스트만** 쓰게 하고, 그 테스트가 현재 동작을 정확히 기술하는지 내가 읽는다. 그 다음에 리팩터링을 맡긴다.

순서를 지키는 게 중요하다. 리팩터링과 테스트 작성을 한 번에 맡기면, 에이전트가 자기가 바꾼 동작에 맞춰 테스트를 쓴다. 그러면 테스트는 통과하지만 아무것도 검증하지 않는다.

## 규칙 2: 한 번에 한 가지 관심사만

두 가지를 같이 맡기면 diff에서 둘이 섞인다. 섞이면 하나가 틀렸을 때 어느 쪽이 틀렸는지 분리해서 볼 수 없다.

구체적으로 이런 조합을 피한다.

- 이름 바꾸기 + 로직 정리 → 이름만 바꾼 줄과 로직이 바뀐 줄을 구분할 수 없다
- 포맷팅 + 기능 수정 → diff의 90%가 공백이라 나머지 10%를 못 본다
- 파일 이동 + 내용 수정 → git이 이동을 추적하지 못해 전체가 새 파일로 보인다

마지막 것은 특히 손해가 크다. 파일을 옮기고 내용까지 고치면 리뷰할 방법이 사라진다. 그래서 이동은 항상 따로, 그리고 내용 변경 없이 한다.

```bash
# 1단계: 이동만
git mv src/util/validator.ts src/domain/order/validator.ts
git commit -m "refactor: validator를 도메인 폴더로 이동"

# 2단계: 내용 수정 (여기서 에이전트에 맡긴다)
```

## 규칙 3: 판단의 근거를 남기게 한다

이게 가장 늦게 추가한 규칙이고, 실제로 가장 많은 시간을 아꼈다.

에이전트에게 "왜 이렇게 했는지 커밋 메시지 본문에 적어달라"고 요청한다. 그러면 두 가지가 생긴다.

첫째, **내가 나중에 그 결정을 되짚을 수 있다.** 넉 달 전 코드를 보면서 "왜 여기만 다르게 처리했지"를 묻게 되는데, 그 답이 히스토리에 있다.

둘째, 이게 더 중요한데, **근거를 적게 하면 근거가 약한 변경이 눈에 띈다.** "가독성을 위해 정리했습니다"만 적힌 커밋은 대개 실제로는 아무 이유가 없는 변경이다. 근거를 요구하면 그런 게 걸러진다.

> **Try:** "커밋 메시지 본문에 이 변경이 필요한 이유와, 고려했지만 택하지 않은 대안 하나를 적어줘."
>
> 대안을 요구하는 게 핵심이다. 대안이 없으면 그건 선택이 아니라 반사다.

## 맡기지 않는 것

규칙 세 개를 다 지켜도 안 맡기는 작업이 있다.

| 작업 | 왜 안 맡기나 |
|---|---|
| 동시성 제어 코드 | 틀렸을 때 테스트가 통과한다. 재현이 확률적이다 |
| 인증·인가 경계 | 틀렸을 때의 비용이 되돌릴 수 있는 범위를 넘는다 |
| 데이터 마이그레이션 | 되돌릴 수 없다. 규칙 1의 전제가 성립하지 않는다 |
| 성능 최적화 | "빨라 보이는" 코드와 "빠른" 코드를 구분하려면 측정이 필요하다 |

공통점은 **잘못을 알아챌 수 있는 수단이 없다**는 것이다. 규칙 1의 반대편에 있는 목록이라고 봐도 된다.

성능 최적화는 조금 다른 이유다. 이건 맡길 수는 있는데, 반드시 측정을 내가 한다. 에이전트가 "이렇게 하면 더 빠릅니다"라고 말한 것 중 실제로 빨라진 것은 절반쯤이었다. 나머지 절반은 빨라 보이는 코드였다.

---

넉 달 써보고 남은 감각은 이렇다. 에이전트는 **내가 무엇을 원하는지 아는 작업**에서 빠르고, **내가 무엇을 원하는지 모르는 작업**에서 위험하다. 후자는 애초에 나 혼자서도 오래 걸리는 일이고, 그때 필요한 건 속도가 아니라 생각이다.
