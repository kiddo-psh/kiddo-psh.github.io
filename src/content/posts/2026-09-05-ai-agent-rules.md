> Claude Code 제작자는 왜 시스템 프롬프트의 80%를 지웠을까?

AI 코딩 에이전트를 팀 프로젝트에 본격적으로 쓰기 시작하면서 가장 먼저 부딪힌 문제는 **사람마다 AI를 쓰는 방식이 너무 다르다는 점**이었습니다.

누군가는 Claude Code에게 기능 전체를 맡겼고, 누군가는 코드 몇 줄 뽑아내는 보조 도구처럼 썼어요. 테스트까지 에이전트에게 맡기는 사람도 있었고, 구현 결과를 거의 그대로 가져오는 경우도 있었죠. 같은 프로젝트를 만들고 있는데도 결과물의 모양과 품질이 꽤 달랐어요.

그래서 다음 프로젝트에서는 반대로 가봤어요.

프로젝트 구조, 개발 규칙, 테스트 방식, 문서화 규칙 등을 자세하게 정리했고, 기능 개발 과정도 `플랜 -> 테스트 작성 -> 구현 -> 리뷰`의 공통 파이프라인으로 맞췄어요.

목표는 단순했습니다.

> **누가 어떤 에이전트를 쓰더라도 일정한 방식으로 개발하게 만들자.**

효과는 있었어요. 이전보다 작업 방식의 편차가 줄었고, 협업도 훨씬 안정적이었거든요.

그런데 프로젝트가 진행될수록 다른 질문이 생기더라고요.

**이 방식이 안정적인 건 알겠는데, 정말 좋은 방식인지는 어떻게 알 수 있을까?**

어떤 단계를 줄였을 때 정말 효율이 좋아진 건지, 규칙 하나를 추가했을 때 실제로 품질이 올라간 건지 판단하기가 어려웠어요. 결국 대부분은 느낌에 의존하고 있었죠.

그런 고민을 하던 중에 Claude Code를 만든 Boris Cherny의 인터뷰를 봤는데요. Claude Code 팀은 제가 했던 것과는 꽤 다른 방향으로 접근하고 있었어요.

---

## 새 모델이 나오면 기존 규칙도 다시 검증해야 한다

모델마다 성격과 능력이 다릅니다. 그래서 몇 달 전 모델에 맞춰 만든 프롬프트나 도구 설정이 다음 모델에서도 그대로 맞는다는 보장은 없다고 Boris는 설명해요.

모델이 원래 알아서 해야 하는데 잘 못하던 행동들이 있었고, Claude Code의 시스템 프롬프트에는 그런 행동을 보완하는 지시가 많이 들어 있었대요. 그런데 Opus 5가 발전하면서 이런 행동을 스스로 할 수 있게 됐고, 그 결과 **시스템 프롬프트의 약 80%를 삭제했다**고 하더라고요.

이 사례에서 눈에 띄었던 건 순서예요. 규칙을 더 추가하기 전에, 필요 없어진 규칙부터 지웠다는 거죠.

## 완벽한 설계보다, 실험에서 시작한다

Boris는 AI 에이전트를 다루는 방식이 **과학 실험**에 가깝다고 말합니다.

기존 소프트웨어 개발에서는 먼저 구조를 설계하잖아요. 아키텍처를 정하고, 시스템 동작을 고민하고, 테스트를 준비한 뒤에 그 위에 기능을 쌓아요. Boris는 이걸 처음부터 하나의 “**big beautiful system**”을 만드는 방식이라고 표현해요.

하지만 AI 모델은 고정된 시스템이 아니에요. 새 모델이 나올 때마다 행동이 달라지거든요. 이전 모델에서 필요했던 지침이 새 모델에서는 불필요할 수도 있고, 예전엔 여러 보조 장치가 필요했던 작업을 새 모델은 혼자서 처리하기도 해요.

그래서 처음부터 모델에게 필요한 모든 규칙을 예측하려고 하지 말고, **직접 써보고 관찰하라**는 거예요.

```text
모델에게 실제 작업을 맡긴다
        ↓
결과와 실패를 관찰한다
        ↓
반복되는 문제를 찾는다
        ↓
필요한 부분만 수정한다
        ↓
다시 실험한다
```

Boris는 이걸 **경험적이고 과학적인 과정**이라고 표현해요.

> **Try something, see the result, and then iterate based on that.**

먼저 완벽한 시스템을 설계해 두고 모델을 그 안에 끼워 넣는 게 아니라,

**모델이 실제로 어떻게 행동하는지 관찰한 뒤에 시스템을 조정하는 거죠.**

AI 에이전트를 위한 개발 환경 자체가 하나의 **실험 대상**인 셈이에요.

Claude Code 팀은 이 과정을 삭제 실험(`ablation`)이라고 불러요. 시스템 프롬프트를 전부 없앤 단순 모드(`simple mode`)로 실행해 보고, 프롬프트가 없는 상태에서 모델의 기본 능력이 더 잘 드러나는지 확인해요. 그다음 필요한 지시를 한 줄씩 다시 넣으면서 각 지시가 실제로 어떤 효과를 내는지 검증하고요. 도구와 실행 환경(`harness`) 코드도 같은 방식으로 제거하고 확인한대요.

물론 제품에는 UX나 안전, 원하는 행동을 위한 지시가 필요할 수 있어요. 다만 처음부터 모든 규칙을 넣어둘 일은 아니고, 각 규칙이 정말 필요한지 실험으로 확인하는 거예요.

그래서 Boris는 사용자에게도 `CLAUDE.md`, skills, hooks를 한 번 지워보라고 조언해요. 새 모델에서는 예전에 필요했던 지시가 더는 필요하지 않을 수 있으니까요.

처음부터 필요한 규칙을 추측할 필요도 없어요. 최소한의 상태에서 모델을 써보고, 같은 문제에서 반복해서 실패할 때만 지침을 다시 추가하면 돼요. 매번 모델의 컨텍스트에 들어가는 규칙이라면 정말 필요한지 한 번은 확인해 봐야 하고요.

## 구체적인 지시가 항상 좋지는 않다

Boris는 인터뷰 후반에서 최신 모델을 쓸 때 흔히 하는 실수 중 하나로 **지나치게 구체적인 지시**를 꼽습니다.

예를 들면 이런 식이에요.

```text
1. 먼저 A를 한다.
2. 다음으로 B를 한다.
3. 반드시 C를 거친다.
4. 마지막으로 D를 수행한다.
```

문제 해결 과정을 하나하나 지정해 주는 방식이죠.

대신 더 높은 수준에서

* 해야 할 일
* 지켜야 할 경계
* 완료 조건

만 알려주고, 모델이 스스로 문제를 풀게 두라고 해요.

이 관점에서 보면 프로젝트가 정의해야 할 건 크게 세 가지로 볼 수 있어요.

```text
WHAT
무엇을 만들어야 하는가?

CONSTRAINT
무엇을 하면 안 되는가?

DONE
언제 작업이 완료되었다고 판단하는가?
```

물론 모든 HOW를 없애야 한다는 뜻은 아니에요. 특정 아키텍처를 반드시 지켜야 하거나 데이터 정합성 때문에 정해진 흐름이 필요한 경우에는 구현 방식 자체가 제약(constraint)이 되죠.

관건은 **그 규칙이 왜 존재하는지**예요.

실제로 품질을 높인다는 근거가 없다면, 그 규칙은 도움이 되는 발판(scaffolding)이라기보다 모델의 컨텍스트와 자유도를 소모하는 제약일 수도 있거든요.

---

## HOW를 맡기려면, 검증할 수 있어야 한다

그런데 여기서 한 가지 의문이 남아요.

**에이전트에게 문제를 푸는 방법까지 맡긴다면, 결과의 품질은 어떻게 보장할까요?**

Boris가 여기서 가장 강조한 건 **검증**(verification)이었습니다.

그는 최근에 중요해진 능력이 좋은 프롬프트를 쓰는 것보다

> 모델에게 조금 어려운 작업을 주고, **스스로 자기 작업을 검증할 수 있게 만드는 것**

에 가까워지고 있다고 말해요.

인터뷰에서 소개한 사례가 인상적이었는데요. Boris는 Claude에게 기존 Electron 기반 데스크톱 앱을 Swift 네이티브 앱으로 다시 만들어 달라고 요청했어요. 그런데 작업 방법을 세세하게 알려주지는 않았대요.

프롬프트는 오히려 단순했어요.

```text
Electron 앱을 실행한다.
Swift 앱을 실행한다.

두 화면을 캡처해서 픽셀 단위로 비교한다.

차이가 있다면 수정한다.
완성될 때까지 반복한다.
```

인터뷰 당시 이 작업은 이미 2주 넘게 돌아가고 있었다고 해요.

Boris가 Claude에게 알려준 건 **자기가 제대로 만들었는지 확인하는 방법**이었어요. 어떻게 Swift 앱을 만들지는 알려주지 않았죠.

모델은 구현 방법을 스스로 고르고, 결과가 틀렸다면 스크린샷 비교로 그 사실을 알아채서 다시 고쳐요.

즉,

```text
목표를 준다
+
검증 방법을 준다
+
실패하면 다시 시도하게 한다
```

이런 방식이에요.

이렇게 보면 앞에서 얘기한 `DONE`, 즉 **완료 조건**의 의미도 조금 달라져요.

완료 조건은 사람이 작업을 확인하는 체크리스트에서 그치지 않아요. 가능하다면 에이전트 스스로

> **“아직 끝나지 않았다.”**

라고 판단할 수 있게 해주는 기준이어야 하는 거죠.

에이전트에게 더 많은 자율성을 주려면 작업 지시를 더 늘리는 것으론 부족할 수 있어요. 필요한 건 **더 명확한 피드백 루프**입니다.

## 지금의 결론

저는 여전히 팀 프로젝트에서 공통된 `AGENTS.md`가 필요하다고 생각합니다. 특히 여러 사람이 서로 다른 AI 에이전트를 쓰는 환경에서는 프로젝트의 구조와 제약을 공유할 기준이 필요하거든요.

다만 목적은 조금 달라졌어요.

> **AI의 모든 행동을 통제하는 문서가 아니라,
> AI가 자유롭게 움직일 수 있는 경계를 알려주는 문서.**

그리고 그 안에 들어가는 규칙은 가능하면 실제 실패를 겪고 나서 필요성이 확인된 것이어야 해요.

에이전트에게 정말 줘야 할 건 상세한 작업 절차가 아니라

> **무엇을 해야 하는지,
> 무엇을 하면 안 되는지,
> 언제 끝났다고 판단할 수 있는지를 명확하게 만드는 것**

이 될 것 같아요.
