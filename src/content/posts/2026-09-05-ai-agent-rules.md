> Claude Code 제작자는 왜 시스템 프롬프트의 80%를 지웠을까?

AI 코딩 에이전트를 팀 프로젝트에 본격적으로 사용하면서 가장 먼저 부딪힌 문제는 **사람마다 AI를 사용하는 방식이 너무 다르다는 것**이었다.

누군가는 Claude Code에게 기능 전체를 맡겼고, 누군가는 코드 몇 줄을 작성하는 보조 도구처럼 사용했다. 테스트까지 에이전트에게 맡기는 사람이 있는 반면, 구현 결과를 거의 그대로 가져오는 경우도 있었다.

같은 프로젝트를 개발하고 있는데도 결과물의 형태와 품질이 꽤 달랐다.

그래서 다음 프로젝트에서는 반대로 접근했다.

`AGENTS.md`를 만들고 프로젝트 구조, 개발 규칙, 테스트 방식, 문서화 규칙을 정리했다. 기능 개발 과정도 어느 정도 공통된 파이프라인으로 맞췄다.

목표는 단순했다.

> **누가 어떤 에이전트를 사용하더라도 일정한 방식으로 개발하게 만들자.**

효과는 있었다.

이전보다 작업 방식의 편차가 줄었고 협업도 훨씬 안정적이었다.

하지만 프로젝트를 진행할수록 다른 질문이 생겼다.

**이 방식이 안정적인 것은 알겠는데, 정말 좋은 방식인지는 어떻게 알 수 있을까?**

어떤 단계를 줄였을 때 정말 효율이 좋아진 것인지, 규칙 하나를 추가했을 때 실제로 품질이 올라간 것인지 판단하기 어려웠다.

결국 대부분은 느낌에 의존했다.

그런 고민을 하던 중 Claude Code를 만든 Boris Cherny의 인터뷰를 보게 됐다.

Claude Code 팀은 내가 했던 것과 꽤 다른 방향으로 접근하고 있었다.

---

## Claude Code는 시스템 프롬프트의 80%를 삭제했다

Boris는 새로운 모델에 맞춰 Claude Code의 **시스템 프롬프트 약 80%를 삭제했다**고 이야기한다.

기존 시스템 프롬프트에는 모델이 부족했던 부분을 보완하기 위한 지시가 많이 들어 있었다.

하지만 모델이 발전하면서 예전에는 명시해야 했던 행동을 이제는 모델이 스스로 수행하기 시작했다.

그렇다면 과거의 지침을 계속 유지할 이유가 있을까?

오히려 필요 없는 지침이 모델의 새로운 능력을 제한할 수도 있다.

Claude Code 팀은 이를 확인하기 위해 시스템 프롬프트와 도구 프롬프트를 제거해보는 **ablation**을 반복한다.

흥미로운 점은 프롬프트를 제거했을 때 모델이 오히려 더 지능적으로 행동하는 경우도 있었다는 것이다.

물론 실제 제품에는 안전, 권한, UX 등을 위한 지침이 필요하다.

중요한 것은 출발점이다.

> **“무엇을 더 넣을까?”가 아니라
> “이 지시가 정말 필요한가?”를 먼저 묻는다.**

---

## 완벽한 설계보다, 실험에서 시작한다

Boris는 AI 에이전트를 다루는 방식을 **과학적 실험**에 가깝다고 설명한다.

기존 소프트웨어 개발에서는 먼저 구조를 설계한다.

아키텍처를 정하고, 시스템의 동작을 고민하고, 테스트를 준비한 뒤 그 위에 기능을 쌓는다. Boris는 이를 처음부터 하나의 **“big beautiful system”**​을 만드는 방식에 비유한다.

하지만 AI 모델은 고정된 시스템이 아니다.

새 모델이 나올 때마다 행동이 달라진다.

이전 모델에서 필요했던 지침이 새로운 모델에서는 불필요할 수 있고, 과거에는 여러 보조 장치가 필요했던 작업을 새로운 모델은 스스로 처리하기도 한다.

그래서 처음부터 모델에게 필요한 모든 규칙을 예측하는 대신 **직접 사용해보고 관찰해야 한다.**

```text
모델에게 실제 작업을 맡긴다
        ↓
결과와 실패를 관찰한다
        ↓
반복되는 문제를 찾는다
        ↓
필요한 부분만 수정한다
        ↓
다시 실험한다
```

Boris는 이를 **empirical하고 scientific한 과정**이라고 표현한다.

> **Try something, see the result, and then iterate based on that.**

먼저 완벽한 시스템을 설계하고 모델을 그 안에 끼워 넣는 것이 아니라,

**모델이 실제로 어떻게 행동하는지 관찰한 뒤 시스템을 조정한다.**

AI 에이전트를 위한 개발 환경 자체가 하나의 **실험 대상**인 셈이다.

## 에이전트에게 HOW까지 정해줘야 할까?

Boris는 인터뷰 후반부에서 최신 모델을 사용할 때 흔히 하는 실수 중 하나로 **지나치게 구체적인 지시**를 이야기한다.

예를 들어,

```text
1. 먼저 A를 한다. 
2. 다음으로 B를 한다. 
3. 반드시 C를 거친다. 
4. 마지막으로 D를 수행한다.
```

처럼 문제 해결 과정을 세세하게 지정하는 방식이다.

대신 더 높은 수준에서

* 해야 할 일
* 지켜야 할 경계
* 완료 조건

을 알려주고 모델이 스스로 문제를 해결하게 두라고 말한다.

이 관점에서 프로젝트가 정의해야 할 것은 크게 세 가지로 볼 수 있다.

```text
WHAT
무엇을 만들어야 하는가?

CONSTRAINT
무엇을 하면 안 되는가?

DONE
언제 작업이 완료되었다고 판단하는가?
```

물론 모든 HOW를 없애야 한다는 뜻은 아니다.

특정 아키텍처를 반드시 지켜야 하거나 데이터 정합성을 위해 정해진 흐름이 필요한 경우에는 구현 방식 자체가 constraint가 된다.

중요한 것은 **왜 그 규칙이 존재하는지**다.

실제로 품질을 높인다는 근거가 없다면, 이런 규칙은 도움을 주는 scaffolding이 아니라 모델의 컨텍스트와 자유도를 소모하는 제약일 수도 있다.

## AGENTS.md도 가설이어야 한다

그래서 지금은 `AGENTS.md`를 조금 다르게 보려고 한다.

예전에는 한 번 만든 규칙을 계속 축적했다.

```text
문제가 생길 것 같다
        ↓
규칙을 추가한다
```

앞으로는 반대로 접근해보고 싶다.

```text
최소한의 규칙으로 작업한다
        ↓
실제 실패를 관찰한다
        ↓
반복되는 실패인지 확인한다
        ↓
필요한 규칙만 추가한다
        ↓
주기적으로 다시 제거해본다
```

즉, `AGENTS.md`는 완성된 정답지가 아니다.

**현재 모델과 현재 프로젝트에 대해 세운 가설의 집합**에 더 가깝다.

새 모델이 나오거나 프로젝트 상황이 바뀌면 이전 규칙도 다시 검증해야 한다.

오래된 규칙은 팀의 노하우일 수도 있지만, 반대로 이미 필요 없어져버린 기술 부채일 수도 있다.

## 지금의 결론

나는 여전히 팀 프로젝트에서 공통된 `AGENTS.md`가 필요하다고 생각한다.

특히 여러 사람이 서로 다른 AI 에이전트를 사용하는 환경에서는 프로젝트의 구조와 제약을 공유할 기준이 필요하다.

다만 목적은 조금 달라졌다.

> **AI의 모든 행동을 통제하는 문서가 아니라,
> AI가 자유롭게 움직일 수 있는 경계를 알려주는 문서.**

그리고 그 안에 들어가는 규칙은 가능하면 실제 실패를 통해 필요성이 확인되어야 한다.

결국 중요한 것은 에이전트에게 상세한 작업 절차를 알려주는 것이 아니라,

> **무엇을 해야 하는지,
> 무엇을 하면 안 되는지,
> 언제 끝났다고 판단할 수 있는지를 명확하게 만드는 것**

일지도 모른다.

그렇다면 다음 질문이 남는다.

**작업 방법을 에이전트에게 맡긴다면 결과의 품질은 어떻게 보장할까?**

Boris가 인터뷰에서 특히 강조했던 것이 바로 이 부분이다.

**Verification.**

다음 글에서는 좋은 프롬프트를 작성하는 것보다 왜 **에이전트가 자신의 작업을 검증할 수 있는 환경을 만드는 것**이 중요해지고 있는지 정리해보려고 한다.
