백엔드 팀의 작업 규칙에는 네 단계가 있었습니다. **플랜 → 실패하는 테스트 먼저 → 구현 → 검토.** 코드가 바뀌면 사람이 단계마다 새 AI 세션을 열어 진행했어요. [앞 글](/posts/ai-rule-docs-cleanup)에서는 이 규칙을 바로 고치지 않고, 방향과 효과를 어떻게 판단할지 먼저 묻겠다고 했습니다.

오타를 고치는 작업과 회원 탈퇴 기능을 바꾸는 작업이 같은 절차를 거쳐야 할까요? 전자는 몇 줄을 확인하면 끝나지만, 후자는 여러 테이블을 지우고 토큰을 폐기하므로 놓친 조건 하나가 다른 사용자에게도 영향을 줄 수 있습니다. 기존 규칙은 둘 다 네 단계로 처리했어요.

이번에는 단계 수를 일괄적으로 줄이는 대신, **어떤 변경에 무거운 검토가 필요한지** 정했습니다. 전체 흐름은 이렇게 바뀌었습니다.

## 모든 변경에 같은 절차가 비쌌다

기존 규칙에서도 문서·주석·테스트 코드만 바꾸면 검증으로 끝낼 수 있었습니다. 하지만 그 밖의 변경은 모두 네 단계를 거쳤고, **애매하면 네 단계가 기본값**이었어요. 그래서 사소한 코드 수정도 별도 플랜, 테스트 선행, 구현, 검토 세션을 열었습니다.

처음에는 테스트 선행을 없앨지, 리뷰 관점을 다섯 개에서 줄일지 고민했습니다. 그런데 그렇게 하면 회원 탈퇴처럼 위험한 변경도 함께 가벼워집니다. 문제는 단계 하나의 비용보다 **서로 다른 작업을 같은 줄에 세워둔 규칙**에 있었어요.

## 바뀐 파일로 세 갈래를 고른다

새 규칙은 먼저 변경한 파일과 코드가 위험 트리거에 해당하는지 봅니다. 트리거가 있으면 다른 조건보다 **게이트가 우선**입니다. API 계약 문서만 바꾼 작업도 여기에 포함됩니다.

| 갈래 | 어떤 변경인가 | 무엇을 하나 |
| --- | --- | --- |
| 검증만 | 위험 트리거에 해당하지 않는 일반 문서·주석·테스트 코드만 변경 | 빌드 확인 |
| 기본 | 위험 트리거가 없는 일반 코드 변경 | 플랜, 구현, 테스트, 빌드를 한 세션에서 완료 |
| 게이트 | 위험 트리거가 하나라도 있는 변경 | 기본 절차에 A·B 독립 리뷰 추가 |

트리거는 막연히 위험해 보이는 항목으로 만들지 않았습니다. 팀이 겪은 사고와 리뷰 지적이 어디서 나왔는지 되짚어 골랐어요. API 명세나 DB 스키마 계약, Flyway 마이그레이션, 인증·인가와 토큰 처리, 트랜잭션 경계, 공용 인프라, 배포 설정 등이 대표적입니다. **되돌리기 어렵거나 다른 담당자에게 번지는 변경**들입니다.

판정도 플랜 첫 줄에 남깁니다. 예를 들어 계정 삭제가 API 계약을 바꾸고 여러 테이블을 한 트랜잭션에서 지운다면, `게이트 · API 계약 변경 · 트랜잭션 경계 변경 · 인가 검토 필요`처럼 씁니다. 나중에 리뷰할 때 어떤 이유로 무거운 절차를 골랐는지 확인할 수 있어요.

## 테스트 선행을 없애고, 기대 결과를 먼저 적었다

기존에는 실패하는 테스트를 **구현 전에 실행**해야 했습니다. 개정 후에는 그 순서를 강제하지 않습니다. 대신 플랜에 기능마다 입력과 기대 결과를 먼저 적고, 구현 뒤 테스트가 그 결과를 확인하는지 봅니다. 기대 결과를 바꾸거나 플랜에 없는 테스트를 추가하면 사람에게 확인받고 변경 이유를 기록합니다.

예를 들어 “잘못된 커서는 400을 돌려준다”를 플랜에 적었다면, 구현이 어려워졌다고 테스트의 기대값을 500으로 바꾸고 조용히 통과시킬 수 없습니다. 실제 리뷰에서도 플랜과 테스트의 기대값이 달라졌는데 변경 기록이 없는 사례를 잡았습니다.

이는 **테스트를 먼저 실행하는 TDD와 같은 방식은 아닙니다.** 테스트 선행의 이점 중 하나였던 “구현 뒤에 합격 기준을 몰래 고치지 않는다”를 기록과 리뷰로 지키는 선택입니다. 테스트는 여전히 존재하고 빌드를 통과해야 합니다.

## 위험한 변경은 두 리뷰어가 다른 질문을 한다

기존 검토에서는 계약, 보안, 테스트를 각각 볼 때 같은 기준 문서를 다시 읽었습니다. 개정 후에는 변경한 코드와 관련 계약 부분을 함께 읽고 여러 관점을 한 번에 적용합니다. 동시성이나 인가 검토는 해당 코드가 바뀌었을 때만 엽니다.

게이트 갈래에서는 한 가지를 더 합니다. 두 AI 리뷰어가 **서로의 결과를 읽지 않고** 같은 변경을 살펴봅니다.

- **A**는 계약, 보안, 테스트 같은 정해진 관점에서 빠진 것을 찾습니다.
- **B**는 “이 기능이 목적을 달성하지 못하는 입력이나 실행 순서가 있을까?”를 묻습니다. 결함을 못 찾았다면 무엇을 시도했는지도 적습니다.

두 결과가 나온 뒤에야 지적을 합쳐 채택·기각·후속 작업을 정합니다. 두 사람이 다른 질문을 하면 테스트가 통과해도 놓친 입력을 찾을 수 있을지 확인하려는 실험이었습니다.

### 한 리뷰어만 찾은 커서 결함

사용자 검색을 검토할 때 A는 차단할 결함을 찾지 못했고 B는 하나를 지적했습니다. 검색 결과의 다음 페이지를 가리키는 **커서**에 NUL 제어문자를 넣는 경우였어요.

```text
커서                  bQBvOjE
해독한 페이지 경계 값  m\x00o:1  (\x00은 NUL을 표시한 것)
```

커서는 겉으로는 영문자만 있는 Base64 문자열입니다. 해독하면 닉네임에 NUL이 들어갑니다. 길이와 구분자만 검사하면 통과하지만, PostgreSQL은 NUL이 들어간 텍스트를 받지 않습니다. B의 리뷰는 이 DB 오류가 서비스의 예외 처리에서 **500 INTERNAL_ERROR**로 이어지는 경로를 지적했습니다.

계약에는 잘못된 커서는 400으로 응답한다고 적혀 있었고, 플랜의 테스트도 여덟 종류의 잘못된 커서를 검사했습니다. 모두 통과했지만 여덟 종류 중에는 제어문자가 없었습니다. A는 **현재 테스트가 계약대로 있는지** 봤고, B는 **그 테스트를 통과하면서 계약을 깨는 입력이 있는지** 봤습니다. 두 질문의 차이가 드러난 사례입니다.

회원 탈퇴를 검토할 때는 반대로 두 리뷰어가 서로를 보지 않고 같은 상위 결함 네 건을 짚었습니다. 독립적으로 같은 지적이 나왔다는 것은 검토할 만한 근거였지만, 그것만으로 결함이 확정되는 것은 아닙니다. 사람은 코드와 계약을 다시 확인한 뒤 채택했습니다.

결함이 없다는 결론에도 시도 목록이 남습니다. 커서 인코딩을 공통 모듈로 묶은 작업에서 B는 공격을 시도한 12건을 기록하고 차단 결함 0건으로 마쳤어요. “문제 없음”만 적을 때보다 **어디까지 확인했는지** 다음 사람이 알 수 있습니다.

## 효과를 판정할 숫자는 아직 비어 있다

절차를 바꾼 방향과 검토 방식은 정했지만, **어느 쪽이 더 효율적인지**는 아직 답하지 못했습니다. 검토 중 읽은 문서 절 수나 발견 사항은 기록했어도, 비용과 놓친 결함이 실제로 줄었는지 비교할 자료가 모이지 않았어요.

규칙에는 게이트 작업의 MR 다섯 건에서 연속으로 **사후 누락 0건**이면 분리 리뷰를 완화할지 검토한다고 적었습니다. 여기서 사후 누락은 AI 리뷰가 놓쳤지만 사람이 MR을 리뷰하면서 뒤늦게 발견한 지적입니다. 기본 갈래에서 사후 누락이 나오면 트리거를 넓힐지도 검토합니다.

시범 작업 다섯 건의 리뷰 파일에는 이 숫자를 넣을 칸이 있습니다. 그러나 다섯 칸 모두 `(병합 후 기입)`으로 남아 있었어요. 측정 칸을 만드는 것과 실제로 채우는 일은 달랐습니다. 다음에는 **사람의 MR 리뷰가 끝날 때** 결과를 기록하게 해야 합니다. 그래야 병합 뒤 다른 일을 시작해도 빠뜨리지 않고, 절차를 언제 가볍게 할지도 판단할 수 있습니다.

추천 파이프라인 담당자도 같은 원칙을 적용했지만, 트리거는 다시 골랐습니다. 백엔드에서는 트랜잭션과 인가가 위험한 자리였다면, 추천 파이프라인에서는 학습·검증 데이터가 섞이는 **데이터 누수**가 그 자리였어요. 절차를 나누는 생각은 옮겨갈 수 있어도 위험 목록은 해당 작업에서 다시 찾아야 합니다.

## 지금의 결론

모든 코드 변경에서 단계를 일괄적으로 줄일 필요는 없었습니다. **가벼운 변경은 한 세션에서 끝내고, 위험한 변경에는 독립 리뷰를 더하는 조건**을 적으면 됩니다. 다만 그 검토가 실제로 비용과 누락을 줄였는지는 아직 모릅니다. 기록하기로 한 숫자를 채운 뒤에야 다음 개정을 판단할 수 있습니다.
