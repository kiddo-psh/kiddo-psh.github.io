## 1. 같은 AI를 쓰면 코드도 비슷해질까?

7명이 4주 동안 AI 기반 주차 위반 감지 시스템을 개발했다. 차량 추적부터 백엔드, 앱, 관리자 웹까지 파트가 나뉘었고, 팀원 대부분이 Claude Code나 Codex를 개발에 적극적으로 사용했다.

![시스템 구조. 카메라와 센서가 Jetson과 Raspberry Pi를 거쳐 Spring Backend로, 다시 앱과 관리자 웹으로 흐른다](/images/retro/01-system-overview.svg)

프로젝트가 끝난 뒤 Git 이력을 살펴보다 예상하지 못한 차이를 발견했다. 같은 팀에서 비슷한 AI 도구를 사용했지만, **에이전트를 사용하는 방식은 사람마다 완전히 달랐다.** 그리고 그 차이는 코드에 그대로 남아 있었다.

## 2. Git 이력에서 발견한 세 가지 차이

프로젝트가 끝난 뒤 저장소의 커밋 이력과 브랜치, 문서 파일을 다시 살펴봤다. 사람마다 에이전트를 쓰는 방식이 세 지점에서 갈렸다.

![팀원별 에이전트 워크플로우 비교. A는 바로 구현, B는 스펙과 계획 먼저, C는 도메인 계약 먼저](/images/retro/02-agent-workflows.svg)

### 코드를 쓰기 전에 무엇을 먼저 쓰는가

에이전트에게 "이 기능 만들어줘"라고 바로 시키는 사람과, 코드 전에 문서를 먼저 쓰게 하는 사람이 있었다.

나는 기능 하나를 시작할 때 문서 두 개를 먼저 만들었다. 무엇을 어떤 기준으로 만들지 적는 설계 스펙과, 어떤 순서로 어떤 파일을 고칠지 적는 구현 계획이다. 그다음 에이전트에게 계획을 태스크 단위로 실행시켰다. 다른 팀원 한 명은 코드 대신 도메인 계약 문서를 먼저 정리했다. 어떤 데이터가 어떤 상태를 거치는지에 대한 약속을 먼저 글로 고정하고, 다음 날 그 약속에 맞춰 코드 구조를 재편했다. 반대편에는 문서 없이 바로 구현해서 몇 시간 안에 머지하는 팀원도 있었다.

저장소에 남은 계획·스펙 문서는 전부 내 커밋이었다. 7명 중 1명만 이 단계를 거쳤다.

### 에이전트에게 어떤 규칙을 넘기는가

Claude Code나 Codex는 저장소 안의 규칙 파일(AGENTS.md, CLAUDE.md)을 읽고 그 기준에 맞춰 코드를 쓴다. 폴더 구조, 이름 규칙, 스타일 토큰, 변경 후 실행할 검증 명령 같은 것을 적어두면 에이전트가 그대로 따른다.

이 파일은 프런트엔드 두 곳에만 있었다. 한 명이 쓰고 다른 한 명이 복제했다. AI 판정, 하드웨어, 백엔드 디렉터리에는 규칙 파일이 없었다. 규칙이 없는 곳에서는 에이전트가 자기 기본값으로 코드를 냈고, 사람마다 다른 그 기본값이 그대로 코드 스타일이 됐다.

### 테스트를 어디까지 쓰게 하는가

에이전트는 시키지 않으면 테스트를 건너뛰기도 하고, 반대로 매번 붙이기도 한다. 팀이 기준을 정하지 않으면 사람마다 결과가 달라진다.

차이를 확인하기 위해 Git diff에서 각 사람이 추가한 전체 코드 라인 중 테스트 파일에 들어간 라인의 비율을 계산했다. 결과는 0%에서 65%까지 벌어졌다. 하드웨어 파트에는 테스트 파일이 100개가 넘었고 프런트엔드에는 한 개도 없었다.

누가 게을렀다는 이야기가 아니다. 테스트를 언제 얼마나 쓸지 아무도 합의하지 않았고, 각자의 에이전트 기본값이 그대로 남은 것이다.

세 가지를 한 표로 정리하면 이렇다.

| 차이 | 한쪽 끝 | 다른 쪽 끝 |
|---|---|---|
| 코드 전에 쓰는 문서 | 설계 스펙 + 구현 계획 | 없음 |
| 에이전트 규칙 파일 | 있음 (프런트엔드 2곳) | 없음 (AI · 하드웨어 · 백엔드) |
| 추가 코드 중 테스트 비율 | 65% | 0% |

## 3. 235줄짜리 기능에 1,400줄 재작업을 하다.

카메라 영상에서 차량을 추적하고 주차 위반을 판정하는 AI 파트는 나와 팀원 A가 나눠 맡았다. A는 기능을 빠르게 구현해서 올리는 방식이었고, 나는 리뷰를 맡았다.

7월 30일 아침, A가 전기차 충전구역 장기 점유 판정 기능을 커밋했다. 235줄짜리 깔끔한 기능 커밋이었다. A는 점심 무렵까지 리뷰 지적 세 건을 스스로 고쳤다. 그 다음이 문제였다.

![7월 30일 타임라인과 코드 양 비교. 내 작업 37분, A 브랜치 재작업 5시간 31분. 기능 커밋 235줄 대 재작업 1,402줄](/images/retro/03-ev-branch-timeline.svg)

> **Feature: 235 LOC**
>
> **Rework: 1,400 LOC / 11 commits / 5.5h**

내 작업은 37분에 압축됐고, 나머지 다섯 시간 반은 A의 브랜치에서 리뷰 지적을 반영하는 데 썼다. 사흘 전 이중주차 브랜치에서도 같은 일이 있었다. A의 기능 커밋 하루 뒤, 나는 하위 브랜치에서 판정 기준 자체를 "시간순 귀책"에서 "구역 침범"으로 바꿨다.

돌아보면 A의 코드가 나빴던 게 아니다. A의 테스트 비중은 45%로 팀 평균 이상이었다. 문제는 **판정 기준을 어떤 근거로 정할지 합의하지 않은 상태에서 에이전트가 그럴듯한 기준을 하나 골라 구현했고, 리뷰에서 그 기준이 뒤집히면 처음부터 다시 고쳐야 했다**는 점이다. 코드 전에 기준을 논의하는 비용을 아끼려다가, 코드가 나온 뒤 다섯 시간의 재작업 비용으로 돌려받은 셈이었다.

## 4. 문제는 코드 스타일이 아니었다

이 패턴이 남긴 비용은 세 가지였다.

**Review Cost.** 저장소 전체의 "리뷰 반영" 커밋 25개 중 22개가 나와 A 사이에서 발생했다.

**Merge Cost.** A의 브랜치는 `develop` 동기화 Merge가 18회로 팀에서 가장 많았다. 브랜치가 오래 열려 있었고 충돌을 계속 풀어야 했다.

**Rework Cost.** 두 사람이 번갈아 쌓은 2,000줄 규모의 베이스라인은 결국 "폐기 예정"으로 표시됐고, 다른 팀원이 구조를 재편한 뒤 수십 개의 정합화 커밋으로 다시 쓰였다.

내 몫도 있다. 내 커밋의 절반 가까이에 Claude 공동 저자 표기가 붙어 있고, A의 코드를 고친 리뷰 커밋들도 에이전트와 함께 썼다.

> **에이전트가 만든 코드를 에이전트로 리뷰하고, 다시 에이전트로 고치는 루프를 사람 둘이 운영하고 있었다.**

지금까지 팀의 코드 품질을 결정하는 변수는 개발자의 코딩 스타일이었다. 그래서 팀은 린터, 포매터, 커밋 규약, 코드 리뷰로 스타일을 맞췄다. 이번에 확인한 것은, **AI가 쓰는 코드의 비중이 커지면 "에이전트를 어떻게 쓰는가"가 코딩 스타일과 같은 급의 변수가 된다**는 점이다.

1. 계획을 먼저 쓰게 하는가, 바로 구현하게 하는가
2. 에이전트에게 어떤 프로젝트 규칙을 넘기는가
3. 테스트를 어디까지 쓰게 하는가

이 세 가지가 사람마다 다르면 같은 모델을 써도 다른 팀이 만든 것 같은 코드가 나온다. 그 차이는 린터로 잡히지 않는다. 리뷰어의 시간으로 메워진다.

## 5. 다음 프로젝트에서는 무엇을 바꿀 것인가

이번 프로젝트에서 문제는 단순히 코드 스타일이 달랐던 것이 아니었다.

구현 전에 기준을 합의하지 않아 **Rework Cost**가 생겼고, 서로 다른 방식으로 개발하면서 **Review Cost**가 커졌으며, 오래 열린 브랜치에서는 **Merge Cost**까지 반복해서 발생했다.

결국 세 비용의 공통 원인은 하나였다.

> **팀원마다 에이전트에게 맡기는 과정과 기준이 달랐다.**

그래서 다음 프로젝트에서는 코드 Convention만 맞추는 데서 한 단계 더 나아가, **에이전트가 작업하는 개발 과정 자체를 팀 단위로 통일해보기로 했다.**

기본적인 개발 흐름은 다음처럼 잡았다.

![팀 공통 개발 파이프라인. Task, Spec, Plan, Implement, Test, Review, Merge 일곱 단계와 모든 단계에 적용되는 AGENTS.md](/images/retro/04-team-pipeline.svg)

각 단계는 첫 프로젝트에서 발생했던 문제를 줄이기 위한 장치다.

* **구현 전 Spec과 Plan을 확인한다.**
  판정 기준처럼 여러 해석이 가능한 요구사항을 코드 작성 전에 합의해, 구현 이후 기준 자체가 뒤집히는 재작업을 줄인다.

* **저장소 루트에 `AGENTS.md`를 둔다.**
  모든 파트의 에이전트가 같은 아키텍처 원칙, 테스트 기준, 커밋·이슈 규칙을 공유하게 해 리뷰 단계에서 반복적으로 맞추던 부분을 앞단으로 옮긴다.

* **테스트 기준을 Pipeline에 포함한다.**
  테스트 작성 여부를 각 개발자와 에이전트의 기본값에 맡기지 않고, 핵심 로직과 경계값이 있는 기능에는 공통된 검증 기준을 적용한다.

* **구현 이후 Review 단계를 공통으로 둔다.**
  기능 동작뿐 아니라 기존 설계와의 정합성, Convention 위반, 테스트 누락을 Merge 전에 확인한다.

* **에이전트 사용 방식도 킥오프에서 합의한다.**
  어떤 AI 도구를 쓰는지만 공유하는 것이 아니라, 어떤 Context를 제공하고 어떤 단계까지 에이전트에게 맡길 것인지도 팀 개발 규칙으로 관리한다.

그래서 이번 프로젝트에서 개발자마다 달랐던

**Planning / Rules / Testing**

을 다음 프로젝트에서는 하나의 **공통 Development Pipeline** 안에 넣어보기로 했다.
