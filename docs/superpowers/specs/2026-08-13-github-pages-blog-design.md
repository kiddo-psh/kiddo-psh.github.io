# kiddo-psh.github.io 블로그 설계

작성일: 2026-08-13

## 1. 목적

백엔드 개발자 취업용 포트폴리오 겸 블로그. 채용담당자가 이력서의 링크를 눌러 들어왔을 때
기술적 판단력과 사고방식을 확인할 수 있어야 하고, 동시에 본인이 부담 없이 계속 글을 쓸 수 있어야 한다.

성공 기준:

- 글 하나 발행에 필요한 작업이 "md 작성 → push" 두 단계로 끝난다.
- 반년간 손대지 않아도 다음에 열었을 때 빌드가 그대로 된다.
- 채용담당자가 3초 안에 무엇을 하는 사람인지, 무엇을 만들었는지 파악한다.

## 3. 정보 구조

| 주소 | 내용 |
|---|---|
| `/` | 프로필 2줄 + 카테고리 탭 + 최신 글 6개(리스트, 라벨 없음) + 하단 프로젝트 카드 (featured 전체, 최대 3개) |
| `/posts` | 전체 글 목록, 카테고리 필터 |
| `/posts/{slug}` | 글 본문 + 목차 + 관련 글 + 댓글 |
| `/projects` | 프로젝트 카드 그리드 |
| `/projects/{slug}` | 문제 → 아키텍처 → 내 역할 → 결과(숫자) |
| `/about` | 소개, 기술 스택, 연락처 |
| `/search` | 사이트 내 검색. 내비게이션의 검색 아이콘이 이 페이지로 연결된다 |
| `/rss.xml` | RSS 피드 |
| `/404` | 404 페이지 |

홈의 프로필 줄 오른쪽에 `프로젝트 N개 →` 링크를 배치한다(N은 실제 프로젝트 수를 자동 계산).
글 우선 구성에서 프로젝트가 스크롤 아래로 내려가므로, 첫 화면에 프로젝트로 가는
진입점이 하나는 있어야 한다.

홈 하단에는 `featured: true` 프로젝트만 `order` 순으로 노출하며 최대 3개까지다.
프로젝트가 1개뿐일 때는 카드가 전체 폭으로 넓게 깔려 빈 자리가 생기지 않게 한다.

## 4. 디렉토리 구조

```
blog/
├─ src/
│  ├─ content/

│  │  └─ projects/        # 프로젝트 상세 (.md)
│  ├─ content.config.ts   # 컬렉션 스키마 정의 (Astro 5+ 규약 경로)
│  ├─ layouts/
│  │  ├─ BaseLayout.astro     # head, nav, footer
│  │  ├─ PostLayout.astro     # 카테고리에 따라 분기
│  │  └─ ProjectLayout.astro
│  ├─ components/
│  │  ├─ Nav.astro, Footer.astro
│  │  ├─ TableOfContents.astro
│  │  ├─ ThemeToggle.astro
│  │  ├─ Search.astro
│  │  ├─ Comments.astro        # giscus
│  │  ├─ PostListItem.astro
│  │  ├─ CategoryTabs.astro
│  │  ├─ ProjectCard.astro
│  │  └─ MetricsTable.astro
│  ├─ pages/
│  │  ├─ index.astro
│  │  ├─ posts/index.astro, posts/[slug].astro
│  │  ├─ projects/index.astro, projects/[slug].astro
│  │  ├─ about.astro
│  │  ├─ rss.xml.ts
│  │  └─ 404.astro
│  ├─ styles/
│  │  └─ tokens.css        # 색·글꼴·간격을 이 파일에만 정의
│  └─ site.config.ts       # 사이트 주소, 이름, 소개, 링크, 카테고리 정의
├─ public/                 # 이미지, favicon, og 기본 이미지
├─ .github/workflows/deploy.yml
├─ .nvmrc                  # 24
├─ astro.config.mjs
└─ package.json
```

각 단위의 책임:

- `site.config.ts` — 사이트 전역 상수의 단일 출처. 이름·소개·깃허브 주소·카테고리 목록이
  여기 한 곳에만 있어서, 문구를 바꿀 때 컴포넌트를 뒤지지 않는다.
- `tokens.css` — 색과 글꼴의 단일 출처. 라이트/다크 두 세트의 CSS 변수만 정의하고
  컴포넌트는 변수만 참조한다. 색을 바꾸려면 이 파일만 고친다.
- `content.config.ts` — 프론트매터 스키마. 유효하지 않은 글은 빌드를 실패시킨다.
- `layouts/` — 껍데기. `content/`의 마크다운은 여기에 아무 의존성이 없어서 레이아웃을
  전부 교체해도 글은 한 글자도 고치지 않는다.

## 5. 콘텐츠 모델

### 5.1 글 (`src/content/posts/*.md`)

```yaml
---
title: "JPA N+1, 목록 API가 느려진 진짜 이유"
description: "쿼리 로그를 켜보기 전까지 원인을 세 번 잘못 짚었다"
pubDate: 2026-08-13
category: dev          # dev | ai | retro | essay
draft: false           # 선택, 기본 false
cover: "/images/n1.png"    # 선택. public/ 기준 절대 경로. 공유 카드 전용 (목록에는 쓰지 않는다)
---
```

`title`, `description`, `pubDate`, `category`는 필수다. `draft`와 `cover`는 선택이며
`draft`의 기본값은 `false`다.

`description`을 필수로 두는 이유: 목록의 요약문, 공유 카드 설명, 검색 결과 스니펫에
같은 문장이 쓰인다. 빠지면 세 곳이 동시에 부실해지므로 빌드가 그 자리에서 막는다.

주소는 파일명에서 날짜 접두사를 떼서 만든다.
`2026-08-13-jpa-n1.md` → `/posts/jpa-n1`. 날짜는 파일 정렬용이며 URL에 넣지 않는다.

카테고리 4개는 고정이며 늘리지 않는다. `dev`는 기술 학습·트러블슈팅·설계,
`ai`는 AI 개발 방법론과 워크플로우, `retro`는 회고, `essay`는 일하는 방식과 가치관이다.
카테고리를 늘리지 않는 이유는 필터의 가치가 개수에 반비례하기 때문이다. 4개면
채용담당자가 기술글만 골라 보거나 사고방식만 골라 볼 수 있지만, 10개면 아무도 안 쓴다.

### 5.2 프로젝트 (`src/content/projects/*.md`)

```yaml
---
title: "쿠폰 발급 시스템"
summary: "동시 요청 1만 건에서 중복 발급 0건"
period: "2026.03 ~ 2026.05"
role: "백엔드 3명 중 API·동시성 설계 담당"
stack: ["Spring Boot", "Redis", "MySQL"]
repo: "https://github.com/kiddo-psh/..."
demo: ""               # 선택
metrics:
  - { label: "p99 응답시간", before: "1,240ms", after: "180ms" }
  - { label: "중복 발급", before: "37건", after: "0건" }
featured: true
order: 1
---
```

`metrics`를 본문 산문이 아니라 구조화된 데이터로 분리한 것이 이 모델의 핵심이다.
카드와 상세 페이지 상단에 `1,240ms → 180ms`가 자동으로 크게 렌더되며, `MetricsTable`
컴포넌트 하나가 두 곳을 담당한다. 문단 안에 묻힌 숫자는 읽히지 않는다.

`metrics`가 없는 프로젝트도 허용한다(빈 배열). 그 경우 카드에는 `summary`만 나온다.

본문은 아래 4단 구조를 따른다. 템플릿이 순서를 강제하므로 글이 자동으로 그 형태가 된다.

1. 문제 — 무엇이 왜 문제였는지
2. 아키텍처 — 어떤 구조로 풀었는지
3. 내 역할 — 팀 프로젝트에서 정확히 무엇을 했는지
4. 결과 — 숫자와 남은 과제

### 5.3 태그: 미도입

태그를 지금 넣지 않는다. 태그의 기능은 "글이 많을 때 좁혀 찾기"인데, 한 태그에 글이
1개면 좁혀지는 것이 없고 글을 쓸 때마다 태그를 고민하는 비용만 발생한다. 본문 전체
검색이 태그가 하던 일의 대부분을 대체한다.

도입 조건과 방식을 미리 정해둔다.

> 같은 주제로 글이 3개 쌓이면 그 주제만 태그로 승격한다.

도입 시 허용 태그를 `site.config.ts`에 배열로 정의하고, 목록에 없는 태그를 쓰면 스키마
검증에서 빌드를 실패시킨다. 태그가 지저분해지는 원인은 임의의 문자열이 새 태그가 되는
자유도이므로, 그 자유도를 없앤다.

## 6. 레이아웃 규칙

### 6.1 카테고리별 분기

`PostLayout`이 `category`에 따라 두 형태로 갈린다.

| | `dev`, `ai` | `retro`, `essay` |
|---|---|---|
| 본문 폭 | 넓게 (약 760px) | 좁게 (약 660px) |
| 우측 목차 | 표시 (sticky) | 숨김 |
| 리드문 글꼴 | Pretendard | 세리프 |
| 본문 행간 | 1.8 | 1.95 |

기술글은 문서처럼, 에세이는 읽을거리처럼 보이게 하는 것이 목적이다. 카테고리가 4개로
고정되어 있어 분기 조건이 단순하다.

### 6.2 글 페이지 구성

**본문을 왼쪽에, sticky 목차를 오른쪽에** 두고 사이를 80px 벌린다. 본문 760px +
여백 80px + 목차 220px 이므로 1100px 페이지 안에서 본문이 페이지 중앙보다 왼쪽에
놓인다. 1040px 이하에서는 목차를 숨기고 본문을 가운데 정렬한다.

목차는 `h2`, `h3`만 수집하고 현재 위치를 강조한다. 목차 자체가 글의 구조 요약이
되어, 채용담당자가 전체 흐름을 먼저 훑을 수 있다.

**DOM에서는 본문이 목차보다 먼저 온다.** 목차를 오른쪽에 두면서 얻은 것으로,
키보드와 스크린리더 사용자가 매 글마다 목차 링크 목록을 지나서 제목에 닿는 문제가
사라진다. 목차가 왼쪽에 있을 때는 시각적 순서와 DOM 순서를 함께 만족시킬 수 없었다.

sticky 여백은 32px이다. 상단 내비게이션이 고정되어 있지 않으므로 가릴 헤더가 없고,
제목의 `scroll-margin-top`도 같은 값으로 맞춘다.

본문 하단 순서: 관련 글 3개 (같은 카테고리 최신순, 현재 글 제외) → 댓글.

### 6.3 목록 표현: 글은 리스트, 프로젝트는 카드

홈과 `/posts`의 글 목록은 **세로 리스트**로 렌더한다. 각 행은 제목과
메타(카테고리·날짜·읽는 시간)뿐이다. **이미지도, 요약문도 넣지 않는다.** 행 사이는
1px 구분선으로 나눈다.

요약문을 빼는 것은 미감 판단이다. 대신 **제목이 글의 내용을 혼자 전달해야 한다**는
제약이 생긴다. 제목을 지을 때 그것을 전제로 삼는다. `description`은 목록에서만
빠졌고 공유 카드, 검색 결과 스니펫, `meta description`에서 계속 쓰이므로 여전히
필수 항목이다.

홈에는 "최근 글" 같은 라벨을 두지 않는다. 프로필 바로 아래 시간순 목록이 오면
그것이 최근 글이라는 것은 설명하지 않아도 읽힌다. 대신 글 제목을 `h2`로 두어
문서 구조가 `h1` → `h2`로 이어지게 한다(라벨을 지우면서 제목 단계가 건너뛰지
않도록). 반면 하단 프로젝트 섹션의 "프로젝트" 라벨은 남긴다 — 그건 다른 종류의
콘텐츠가 시작된다는 정보이고, 없으면 글 목록과 구분되지 않는다.

> 이 항목은 처음에 카드 그리드로 정했다가 구현 후 리스트로 되돌린 것이다.
> 되돌린 이유를 남긴다.

카드가 성립하려면 썸네일이 정보를 담아야 한다. 그런데 이 블로그는 글마다 이미지를
만들지 않기로 했고(그 부담이 발행을 늦추는 가장 흔한 원인이므로), 대안으로 넣은
카테고리 라벨 그라데이션 타일은 **글이 여러 편일 때 거의 똑같은 타일이 반복된다.**
반복되는 장식은 정보가 아니라 잡음인데, 그 타일이 카드 높이의 절반 이상을 차지했다.

밀도도 리스트가 낫다. 같은 화면에 카드는 6편이 들어가는데 리스트는 그 두 배가
들어간다. 글이 수십 편으로 늘어날수록 차이가 커진다.

`cover`는 목록에 쓰지 않는다. 공유 카드 전용이다. 일부 글에만 썸네일이 붙으면 행의
높이가 들쭉날쭉해지고, 그러면 훑기라는 리스트의 목적이 깨진다.

**프로젝트는 카드로 유지한다.** 성과 숫자(`1,240ms → 180ms`)와 기술 스택처럼 카드가
실제로 담을 내용이 있고, 개수가 적어 훑는 대상이 아니라 보는 대상이다. 같은 사이트에서
표현을 다르게 쓰는 것은 두 목록의 성격이 다르기 때문이다.

카드 그리드는 **최대 2열**이다(최소 폭 360px). 3열로 갈라지면 카드가 좁아져 성과
숫자가 눌리는데, 그 숫자가 이 포트폴리오에서 가장 값어치 있는 요소다. 프로젝트는
개수를 나열하는 것보다 하나하나를 크게 보여주는 편이 목적에 맞다. 카드의 대표 숫자는
넓어진 자리를 써서 헤드라인 크기로 키운다.

필터는 카테고리 탭 4개로 충분하다. 사이드바 형태의 다중 필터는 만들지 않는다.

## 7. 디자인 토큰

`src/styles/tokens.css`에 라이트/다크 두 세트만 정의한다.

라이트(기본):

| 역할 | 값 |
|---|---|
| 배경 | `#FBFAF7` |
| 본문 | `#23211D` |
| 보조 텍스트 | `#57534A` |
| 경계선 | `#E6E1D6` |
| 액센트 | `#1D6B4F` |
| 코드 배경 | `#F4F1EA` |

다크: 배경 `#191817`, 본문 `#EDEAE3`, 보조 `#A8A199`, 경계선 `#2E2B27`,
액센트 `#4FBE8F`, 코드 배경 `#211F1C`.

다크는 라이트의 역할을 뒤집은 것뿐이며 색 조합을 새로 만들지 않는다. 유지할 팔레트가
하나여야 나중에 색을 바꿀 때 두 곳이 어긋나지 않는다.

액센트는 링크, 카테고리 라벨, 성과 숫자에만 쓴다. 액센트가 나타나는 위치가 곧
"중요한 것"으로 읽히므로 그 외에는 쓰지 않는다.

글꼴과 크기:

본문 기본 크기를 **19px**, 행간을 1.8로 둔다. 긴 기술글을 화면으로 읽는 상황을
기준으로 잡은 값이며, 일반적인 16~17px보다 크다. 글 제목은 `2.1em`, 리드문은 `1.1em`으로
두어 제목 → 리드문 → 본문의 단계가 분명히 보이게 한다.

- UI·본문: Pretendard (self-host 또는 CDN, `woff2`)
- 세리프(에세이 리드문): 시스템 세리프 스택 — 별도 웹폰트를 추가하지 않는다
- 코드: 시스템 모노 스택 (`ui-monospace, SFMono-Regular, Consolas, monospace`)

웹폰트를 Pretendard 하나로 제한한다. 폰트 파일이 늘어나면 첫 로딩이 눈에 띄게 느려지고,
그 대가로 얻는 것이 적다.

## 8. 기능

| 기능 | 구현 |
|---|---|
| 검색 | Pagefind — 빌드된 HTML을 색인. 본문 전문 검색 |
| 목차 | Astro가 추출한 heading으로 생성, sticky + 현재 위치 강조 |
| 다크모드 | CSS 변수 교체, `localStorage` 저장, 최초 방문은 OS 설정 따름 |
| 댓글 | giscus (GitHub Discussions) |
| RSS | `@astrojs/rss` → `/rss.xml` |
| sitemap | `@astrojs/sitemap` |
| 공유 카드 | `cover` 없으면 빌드 시 제목·카테고리로 자동 생성. SNS 공유 전용이며 목록에는 쓰지 않는다 (§6.3) |
| 코드 하이라이팅| Shiki (Astro 내장), 라이트/다크 테마 각각 지정 |

공유 카드를 자동 생성하는 이유: 글마다 썸네일을 만들어야 하면 이미지 작업이 발행을
지연시킨다. 기본은 자동, 좋은 이미지가 있을 때만 `cover`로 덮어쓴다.

다크모드 최초 렌더 시 색이 번쩍이지 않도록, 테마 결정 스크립트는 `<head>`에서
동기적으로 실행한다.

## 9. 배포와 자동화

```
로컬 md 작성 → npm run dev (localhost:4321, draft 포함 확인)
             → git push main
GitHub Actions: npm ci → astro build → pagefind 색인 → 공유카드 생성
             → 성공: GitHub Pages 배포 (2~3분)
             → 실패: 배포 중단 + 메일 알림, 기존 사이트 유지
```

Pages 소스는 브랜치가 아니라 GitHub Actions로 설정한다. `dist/`를 커밋하지 않아
히스토리가 깨끗하다.

의존성 고정 — Astro 선택의 유일한 약점인 "방치하면 빌드가 깨진다"를 막는 장치다.

- `package-lock.json`을 커밋하고 CI는 `npm ci`만 사용한다 (`npm install` 금지).
- Node 버전을 `.nvmrc`와 워크플로우에 `24`로 동시에 명시한다.
- Dependabot 자동 PR은 켜지 않는다. 처리하지 않는 알림은 부채만 남긴다.
  대신 반년에 한 번 수동 업데이트하고, 그때 깨지면 그 자리에서 고친다.

## 10. 검증

이 프로젝트에 단위 테스트는 두지 않는다. 로직이 거의 없고 대부분이 렌더링이라
테스트 유지 비용이 얻는 것보다 크다. 대신 다음 세 가지가 검증을 담당한다.

1. **스키마 검증** — 프론트매터가 스키마에 맞지 않으면 빌드가 실패한다.
   오타(`category: devv`), 필수 필드 누락, 날짜 형식 오류가 여기서 잡힌다.
2. **빌드 성공 = 배포 조건** — 실패 시 배포하지 않으므로 깨진 페이지가 공개되지 않는다.
3. **로컬 확인** — `npm run dev`로 발행 전에 직접 본다.

수동 확인 항목(최초 구축 시 1회):

- 라이트/다크 양쪽에서 모든 페이지 확인
- 모바일 폭에서 목차·카드 그리드가 깨지지 않는지 확인
- 카톡·슬랙에 링크를 붙여 공유 카드가 뜨는지 확인
- 검색에서 한글 단어가 걸리는지 확인
